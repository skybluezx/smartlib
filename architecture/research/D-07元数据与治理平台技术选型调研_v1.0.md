# D-07 元数据与治理平台技术选型调研 v1.0

- 状态：调研完成，等待项目负责人确认
- 日期：2026-08-26
- 关联决策：D-07、ADR-0008（提议）
- 推荐结论：当前采用 SmartLib 最小治理域主路线；OpenMetadata POC 延后至首批真实数据源和技术元数据进入后；DataHub 与 Apache Atlas 暂不进入首轮

## 1. 决策范围

D-07 决定谁负责 SmartLib 的数据源目录、数据契约、许可、质量、责任、来源追溯和治理状态。它不决定外部数据如何搬运（D-06），也不允许通用元数据产品替代 SmartLib 的知识对象、电子资源许可、画像版本、关系证据和智能治理模型。

即使 Demo 使用模拟数据，治理域也不能整体跳过。领导和用户需要看到：

- 数据/资源来自哪里、由谁负责；
- 哪些用途被允许，许可何时到期；
- 哪些内容是业务事实、证据、分析或算法推断；
- 数据质量问题在哪里、由谁处理；
- 某个对象、关系或结果如何回溯；
- 谁访问、修改、审核或拒绝了什么。

## 2. 当前工程事实

已有基础：

- `source_system`：来源、责任部门、类型和授权状态；
- `source_reference`：规范对象到外部 ID、版本、校验和和原始引用的映射；
- `evidence_record` 与 `relation_evidence`：对象/关系证据；
- `policy_tag`：可见性、许可、用途、保留、导出和模型使用标签；
- `knowledge_object` 与 `relation_assertion`：质量、审核、事实类别、版本和双时间；
- append-only `audit_event`；
- RLS、Outbox、搜索和图投影。

仍缺少：

- 数据资产/数据集目录及字段模式版本；
- 可执行的数据使用许可台账；
- 数据契约及变更历史；
- 质量规则、运行结果、问题、责任人和处置闭环；
- 治理汇总和对象来源追溯 API；
- 真实治理页；
- 与通用元数据平台的投影边界。

当前 Web 治理页中的许可数量、数据源数量、拦截次数、质量问题和许可矩阵仍是前端展示 fixture，不能作为当前平台治理事实。

## 3. SmartLib 必须自有的最小治理域

无论是否引入第三方产品，以下数据必须由 SmartLib PostgreSQL 权威保存：

1. `governance_domain`：电子资源、科研、人事、组织、学科等责任域；
2. `data_asset` / `data_asset_version`：数据集、API、文件集合、技术表和发布数据产品；
3. `data_schema_field`：字段、类型、含义、敏感性和用途；
4. `data_contract` / `data_contract_version`：模式、所有者、更新、质量、许可和 SLA 约定；
5. `license_grant`：资源范围、用户范围、允许/禁止用途、内容粒度、有效期和依据；
6. `quality_rule` / `quality_run` / `quality_issue`：规则、结果、严重性、责任和处置；
7. `stewardship_assignment`：责任部门、数据管理员、许可联系人和复核人；
8. `governance_change`：许可、契约、规则和审核状态变更；
9. 现有 `source_reference`、证据、策略标签和审计作为追溯链。

这个模型面向学校知识基础设施，而不是复制一个通用数据目录。外部元数据产品只能接收技术元数据投影或向 SmartLib 提供技术扫描结果。

## 4. 候选方案

### A. SmartLib 最小治理域（推荐当前主路线）

优势：

- 直接覆盖电子资源许可、证据、画像、知识关系和模型使用边界；
- 复用 PostgreSQL 18、FastAPI、RLS、审计和现有前端；
- 可以立即把治理页改为真实 API + synthetic seed；
- 不需要在 Demo 阶段部署第二套数据库、搜索和调度平台；
- 未来仍可把技术元数据投影到 OpenMetadata/DataHub。

风险：

- 不能长期自研完整技术目录、自动血缘、数百连接器和通用质量引擎；
- 必须严格控制范围，只建设 SmartLib 不可替代的治理语义与展示闭环。

### B. OpenMetadata 1.13.x（推荐真实数据阶段 POC）

当前官方项目显示 1.13.0 为最新主版本，Apache 2.0。它提供连接器、技术目录、所有者、域/数据产品、术语、血缘、质量测试、数据契约、事件和治理 UI。

适合未来承担：

- 数据库、管道、消息、仪表板等技术元数据扫描；
- 表/字段级目录、技术血缘和通用数据质量；
- 数据管理员后台检索、补充说明和影响分析；
- 将技术资产上下文投影给 SmartLib。

当前延后原因：

- D-06 真实外部接入已延后，目前没有足够技术资产和血缘供 POC；
- 官方文档显示其生产部署需要独立服务器、数据库、Elasticsearch/OpenSearch，并通常还需要 ingestion/orchestration，资源和升级成本明显；
- 数据契约当前重点围绕 Table 资产，不能直接覆盖电子资源合同许可、知识证据和对象画像；
- 先部署会形成漂亮但空的第二治理界面，反而削弱当前平台真实性。

未来 POC 的正确角色是“技术元数据投影/治理加速器”，不是 SmartLib DataHub 权威模型。

### C. DataHub 1.7（暂不进入首轮）

DataHub 采用 Apache 2.0，事件化 entity/aspect 模型、技术目录、血缘、域、数据产品、契约、断言和 API 生态成熟。当前 1.7 升级记录同时显示较复杂的协调版本、Helm、数据库、搜索和升级顺序。

不优先原因：

- 产品名称与 `SmartLib DataHub` 冲突，用户沟通和运维命名容易混淆；
- 部署和事件化架构较重，当前没有规模证据支持；
- 自定义 aspect 虽灵活，但把 SmartLib 许可/证据语义嵌入其中会增加平台耦合；
- 与 OpenMetadata 同时 POC 没有当前价值。

触发条件：学校已有 DataHub，或真实规模/事件化元数据需求证明 OpenMetadata/最小域不足。

### D. Apache Atlas 2.5（不推荐当前路线）

Atlas 支持类型系统、分类、术语、血缘、搜索以及与 Ranger 的分类授权联动，适合已有 Hadoop/Hive/HBase/Kafka/Ranger 体系的组织。

SmartLib 当前没有上述生态基础。引入 Atlas 会把治理平台选择绑定到不需要的 Hadoop 故障域和运维栈，现代数据库、API、电子资源和知识对象仍需大量自定义。因此不进入首轮。

## 5. 比较矩阵

| 维度 | SmartLib 最小域 | OpenMetadata 1.13.x | DataHub 1.7 | Atlas 2.5 |
|---|---|---|---|---|
| 当前角色 | **权威治理主路线** | 真实数据阶段 POC | 条件候选 | 不推荐 |
| 电子资源许可 | 强，按 SmartLib 建模 | 自定义映射 | 自定义 aspect | 自定义类型 |
| 知识对象/证据/画像 | 强 | 非原生 | 非原生 | 非原生 |
| 技术目录与连接器 | 只建必要部分 | 强 | 强 | Hadoop 生态强 |
| 技术血缘 | 基础来源链 | 强 | 强 | 强 |
| 通用质量测试 | 最小规则闭环 | 强 | 强 | 需扩展 |
| Demo 当前价值 | 高 | 低到中，数据不足 | 低 | 低 |
| 部署复杂度 | 低 | 中高 | 高 | 高 |
| 产品锁定 | 低 | 中 | 中高 | 中高 |
| Apache 2.0 | 项目自有 | 是 | 是 | 是 |

## 6. 推荐决策

建议项目负责人确认：

> SmartLib 采用最小治理域主路线，当前直接在 PostgreSQL/FastAPI 建设来源、资产、数据契约、电子资源许可、质量问题、责任和审计闭环，并把治理页接入真实 API；OpenMetadata POC 延后到首批真实数据源和技术元数据进入后，以技术目录、血缘和通用质量加速器身份评估，不替代 SmartLib 权威治理模型；DataHub 与 Atlas 暂不进入首轮。

## 7. 当前实施价值链

确认后优先形成一条可向领导展示的真实治理链：

```text
synthetic 数据源/电子资源
  → 责任部门与许可登记
  → 数据资产与契约
  → 质量规则和问题
  → 对象/关系/证据
  → 权限或许可判定
  → 审计与治理驾驶舱
```

治理页的数字全部来自数据库汇总；点击资源可看到许可用途与有效期；点击质量问题可看到责任人和状态；点击对象可回溯来源和证据。未来 OpenMetadata 只增加技术元数据，不改变这些能力契约。
