# D-04 搜索与首期向量技术选型调研 v1.0

- 状态：已完成，POC 主路线于 2026-08-25 确认
- 日期：2026-08-25
- 关联决策：D-04、ADR-0005（提议）
- 决策结论：OpenSearch 3.8.x 作为真实 POC 主路线，PostgreSQL 18 全文检索 + pgvector 0.8.6 作为同场基线；POC 达标后才成为首版实施产品

## 1. 这项决策解决什么

SmartLib 的检索底座要同时服务 Web、Public API、MCP、Skill、Agent、小程序和客户端，而不是为某个页面提供私有搜索。它需要覆盖：

- 中文和中英文混合的关键词检索、短语、别名、机构名和精确标识符；
- 学者、成果、项目、专利、资源和需求等对象的过滤、分面与聚合；
- 关键词、语义向量和后续图关系的混合召回；
- 在召回前应用身份、可见性、许可、用途和策略版本约束；
- 返回证据、对象版本、召回通道和可解释排序信息；
- 权限变化快速失效，并可由 PostgreSQL 权威状态和对象存储全量重建。

搜索引擎不是权威库。应用不得直连搜索产品，所有查询必须经过统一查询服务和稳定能力契约。

## 2. 当前已知事实与证据缺口

### 已确认

1. PostgreSQL 18 是权威主库，Outbox 是可靠投影事件源。
2. 当前知识对象模型已经有类型、名称、描述、可见性、审核状态、扩展属性、有效时间和系统时间。
3. 搜索、向量和图是可重建投影；产品替换不能改变上层业务语义。
4. 许可不仅是用户角色，还涉及动作、目的、资源、用户群、网络环境、到期时间、TDM、向量化、模型输入和再发布。
5. 首期不单独引入 Qdrant、Milvus 等专用向量数据库。

### 尚缺证据

- 当前数据库只有极少量开发对象，不能据此评价中文相关性、混合召回或容量。
- 尚未获得学校首批授权真实样本、标准查询集、专家相关性判断和目标并发。
- 尚未确认学校是否已有 Elastic/OpenSearch 集群、运维团队、许可或采购合同。
- 尚未确认电子资源合同是否允许对摘要或全文生成向量。
- 嵌入模型、切片方法和重排模型属于后续独立决策，不能由搜索产品选择隐式锁定。

因此，本轮只能确定候选路线和淘汰门槛，不能声称某引擎已在 SmartLib 真实数据上胜出。

## 3. 候选方案

### A. OpenSearch 3.8.x（推荐 POC 主路线）

适配点：

- Apache 2.0 许可、可自托管，适合校内部署和可替换边界；
- 同一引擎提供 BM25 全文检索、聚合、`knn_vector` 和混合查询；
- `hybrid` 顶层查询可对全部子查询应用一个前置过滤器，符合“先限制候选集再召回”的方向；
- 可使用 RRF 或分数归一化融合。RRF 不要求词法分数和向量分数同尺度，适合作为未调参时的起点；
- k-NN 支持高效过滤；中文可比较内置 CJK bigram 与 ICU 分词/归一化；
- Security 插件提供文档级安全，可作为平台授权之外的纵深防护。

风险与边界：

- 新增 JVM 搜索集群、索引模板、快照、升级、容量和安全运维；
- OpenSearch 官方基准中，RRF 在六个 BEIR 数据集上的平均 NDCG@10 比基于分数的混合管道低 3.86%，所以不能把 RRF 当作默认最优结论；
- 文档级安全只约束读取，不应授权普通调用方直接写索引；平台查询服务仍是唯一业务入口；
- ICU 分析比 CJK 分析消耗更多 CPU/内存，中文方案必须用真实名称、术语和中英混合查询评测；
- 当前最新版为 3.8，但 POC 和生产应固定到经过安全与兼容审查的具体 3.8.x 补丁版，不使用浮动 `latest`。

首版明确不采用：

- 不让 OpenSearch 托管领域权威状态；
- 不由浏览器、MCP 客户端或 Agent 直接访问 OpenSearch；
- 不在首期启用 OpenSearch 内部 Agent/ML 工作流作为平台编排核心；
- 不默认部署 Dashboards 为业务运行依赖；
- 不把嵌入模型选择并入 D-04。

### B. PostgreSQL 18 FTS + pgvector 0.8.6（同场基线/低复杂度备选）

适配点：

- 与当前权威库、RLS、事务、备份和运维体系一致，首版组件最少；
- PostgreSQL 全文检索支持解析器、字典、同义词、排名、摘要和 GIN 索引；
- pgvector 支持精确检索、HNSW、IVFFlat 及过滤，并可从 0.8.0 起使用迭代扫描改善过滤后结果不足；
- 非常适合先验证稳定搜索契约、精确名称和后台管理查询。

风险与边界：

- PostgreSQL 官方全文检索是可扩展框架，但没有证据证明内置配置可直接满足 SmartLib 中文专业分词；中文插件、扩展生命周期和升级兼容需另测；
- pgvector 近似索引通常先扫描再过滤，高选择性许可过滤可能返回少于 `k` 个结果；迭代扫描改善但不消除容量和召回评测责任；
- 官方文档明确，多租户共享近似索引时，一个租户会影响其他租户的召回和速度；必要时需分区或分表；
- 复杂聚合、独立扩容、检索调优和搜索运维工具不如专用引擎完整；
- 把搜索负载放进权威库会增加资源争用，必须有连接池、超时、资源隔离和退出阈值。

该方案不是“伪系统”。如果真实规模和质量证明它足够，可作为首版正式实现；但必须保留 `SearchPort`，避免数据库查询语法泄漏给入口层。

### C. Elasticsearch 9.4.x（条件候选）

适配点：

- 全文、向量和混合搜索能力成熟，官方建议使用 RRF 组合全文和向量结果；
- 如果学校已有受管 Elastic 平台、团队、监控和采购权益，边际运维成本可能最低。

风险与边界：

- 2026-08-25 官方最新版本为 9.4.4，但不能只按最新版选择；
- Elasticsearch/Kibana 源码可在 AGPLv3、SSPL 或 ELv2 下使用，官方发行版仍按 ELv2 提供；
- 文档级/字段级安全、RRF 等能力的可用层级必须按学校实际订阅和合同逐项核验，不能以“源码开放”推导“所需生产功能免费”；
- 如果学校没有既有平台和采购权益，相比 OpenSearch 会引入额外法务、采购和版本边界。

只有在学校提供准确的部署版本、订阅层级、可用功能和运维责任后，才将它加入实测主线。

### D. Qdrant / Milvus 等专用向量库（本轮不选）

首版没有数据证明需要把向量与全文、聚合拆成独立系统。只有当同一数据集上的召回、过滤延迟、容量或成本证明 OpenSearch/pgvector 无法满足目标时，才启动新 ADR。

## 4. 面向 SmartLib 的比较

以下是基于当前架构约束的判断，不是通用产品排名。最终结果以同一 POC 为准。

| 维度 | OpenSearch 3.8.x | PostgreSQL 18 + pgvector 0.8.6 | Elasticsearch 9.4.x |
|---|---|---|---|
| 中文关键词与字段权重 | CJK/ICU 可配置，需真实评测 | 需扩展中文解析能力并验证升级 | 成熟，仍需分析器实测 |
| 精确名称/标识符 | 强 | 强 | 强 |
| 分面与聚合 | 强 | 中，需 SQL 设计 | 强 |
| 混合召回 | 原生管道，RRF/分数融合 | 应用层融合 | 原生，官方推荐 RRF |
| 高选择性向量过滤 | 原生高效过滤，需测 recall | ANN 过滤有结果不足风险 | 原生，需实测 |
| 权限纵深 | DLS + 平台前置过滤 | RLS + 平台前置过滤 | DLS/FLS 依订阅核验 |
| 组件与运维成本 | 中高 | 最低，但占用权威库资源 | 取决于既有平台/订阅 |
| 独立扩容 | 强 | 弱 | 强 |
| 许可确定性 | Apache 2.0 | PostgreSQL/pgvector 开源许可 | 发行版与功能订阅需核验 |
| 当前定位 | **POC 主路线** | **必须同测的基线与退路** | **有既有平台时加入** |

## 5. 推荐决策

建议项目负责人确认：

> SmartLib 采用 OpenSearch 3.8.x 作为搜索与首期向量投影的 POC 主路线，同时以 PostgreSQL 18 全文检索 + pgvector 0.8.6 作为同场基线。只有真实授权样本上的权限零泄漏、中文相关性、混合召回、延迟、资源、投影一致性和重建验收全部通过，才接受 OpenSearch 为首版实施底座。首期不单设专用向量库，Elasticsearch 仅在学校已有平台和许可权益明确时加入 POC。

这不是对 OpenSearch 的无条件确认。它将产品选择拆成两个可追溯步骤：

1. 现在确认 POC 主路线和评价方法；
2. POC 证据完成后，ADR-0005 才能由“提议”变为“已接受”，并启动正式投影实现。

## 6. 稳定架构边界

无论最终选择哪一种产品，都必须保持：

1. `SearchPort` 暴露领域查询语义，不暴露 OpenSearch DSL、SQL 或产品 SDK。
2. 统一查询服务形成身份、角色、组织、可见性、许可用途、网络环境和策略版本上下文。
3. 每个召回通道都应用前置过滤；合并后、进入模型前再做一次策略校验。
4. 搜索结果只返回稳定对象 ID、字段摘要、证据 ID、对象版本、投影版本、召回通道和解释信息。
5. PostgreSQL 业务事务与 Outbox 原子提交，投影消费者幂等处理并记录水位。
6. 权限/许可事件为高优先级；失效完成前采用拒绝优先，而不是继续返回旧可见结果。
7. 使用版本化索引和别名切换完成零停机重建；允许按对象、来源和策略版本重放。
8. Web、API、MCP、Skill、Agent、小程序和客户端共享同一 `search_knowledge` 能力，不复制检索规则。

## 7. 版本与复审规则

- POC 固定具体镜像摘要和补丁版本；不得使用 `latest`。
- OpenSearch 大版本/插件升级必须重跑中文分析、权限、混合相关性、快照恢复和重建测试。
- pgvector 升级必须重跑精确基线、ANN recall、过滤后结果数和 PostgreSQL 18 兼容测试。
- 嵌入模型或切片策略变化视为索引模式变化，生成新投影版本，不覆盖旧版本后静默生效。
- 若学校提供受管 Elastic/OpenSearch 或强制国产化搜索产品，按同一查询集和安全门槛重新 POC。
