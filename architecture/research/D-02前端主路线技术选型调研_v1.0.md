# D-02 前端主路线技术选型调研 v1.0

- 状态：已决策
- 日期：2026-08-25
- 关联决策：D-02
- 当前建议：React 19.2 + TypeScript 6.0 + Vite 8，采用 React Router 7 Data Mode、TanStack Query 和 OpenAPI 生成客户端
- 最终决定：确认采用上述主路线（ADR-0004）

## 1. 这项决策决定什么

D-02 决定 SmartLib **校内 Web 平台**的长期前端主路线，包括页面路由、类型边界、服务端状态、权限展示、测试、构建和静态部署方式。它不决定小程序、原生客户端或公开门户必须使用相同 UI 框架。

所有渠道共享的是能力契约、身份与授权语义、设计令牌和产品语言，而不是强制共享同一套组件代码：

- Web 调用版本化 REST/OpenAPI 和后续 SSE；
- 小程序使用独立渠道适配器和小程序组件体系；
- 桌面或原生客户端可复用生成 SDK、设计令牌和业务术语；
- MCP、Skill 和 Agent 复用能力目录，不依赖 Web 组件；
- 公开门户若确认需要 SEO、公开索引、内容预渲染或独立发布，可在 `apps/public-web` 使用 SSR/SSG 框架，而不迫使校内工作台承担 Node 服务端运行面。

## 2. 当前仓库事实

当前 `apps/web` 是可运行的 React/Vite SPA，已经包含七个产品工作区和成熟的视觉样式，但仍处于工程化迁移前状态：

| 事实 | 当前状态 | 影响 |
|---|---|---|
| React 资产 | 现有页面、交互和图标均为 React JSX | React 路线可渐进迁移，不需重做界面 |
| 组件结构 | `App.jsx` 435 行，七个工作区集中在一个文件 | 需要按路由、功能和公共组件拆分 |
| 类型 | 全部 JavaScript，无 TypeScript 配置 | API、权限和复杂对象缺少静态边界 |
| 路由 | 以 `active` 状态切页，无 URL 路由 | 无深链接、刷新恢复、路由权限和代码分割 |
| 服务端状态 | 仅一处直接 `fetch` | 缺少缓存、失效、错误、重试和统一鉴权处理 |
| 数据 | 六个工作区仍读取 `src/data.js` | 必须迁为测试 fixture 或真实 API |
| 契约 | 已有 FastAPI OpenAPI，但前端未生成客户端 | 手写请求容易发生类型和兼容漂移 |
| 测试 | 无单元、组件或端到端测试 | 当前只有构建成功，不能证明交互和权限正确 |
| 部署 | Vite 静态产物 + Nginx，同源代理 FastAPI | 简单、私有化友好，当前已验证可运行 |

因此，D-02 不是从零选择绿色项目框架。是否保留现有 React 投资和已经验证的静态部署拓扑，是权重最高的事实。

### 2.1 当前基线实测

2026-08-25 对当前工作树进行只读审计与生产构建，得到：

- lockfile 实际解析为 React/React DOM 19.2.8、Vite 7.3.6、`@vitejs/plugin-react` 4.7.0；
- `npm audit --audit-level=high` 返回 `0 vulnerabilities`；
- 当前生产构建成功，JavaScript 为 363.19 kB（gzip 103.91 kB），CSS 为 40.83 kB（gzip 8.52 kB）；
- 构建共转换 4,571 个模块，尚未做路由级代码分割；
- 当前 Node 22 容器实际为 v22.23.2，满足 Vite 8 要求的 Node 22.12+；
- 现有 `package.json` 仍以宽泛版本范围声明依赖，lockfile 与声明版本表达不一致，确认路线后应改为受控升级策略。

这些结果说明当前 React 资产没有必须立即换框架的安全或构建故障；D-02 的主要动因是长期工程化，而不是抢修。103.91 kB gzip 的当前脚本也未形成需要 SSR 才能解决的首屏证据，但七个工作区集中打包，后续仍应通过路由分割建立预算并持续测量。

## 3. 已确认的上游约束

1. Python/FastAPI 是唯一平台核心能力层；Web 不拥有第二套领域规则。
2. PostgreSQL 18 是权威状态；浏览器不能直连数据库。
3. Web、API、MCP、Skill、Agent、小程序和客户端共享 OpenAPI/能力目录，不复制业务语义。
4. 首版采用 Compose，后续迁移 Kubernetes；Web 镜像应保持无状态。
5. 隔离的 synthetic Demo 可使用明确标记的测试身份；D-08 已延后，任何真实用户/数据、试点生产或外部接口开放前必须恢复并接入正式统一身份。
6. 校内工作台当前不要求搜索引擎索引；公开门户需求尚未确认。
7. 尚未接通的数据必须明确标记为 fixture/demo，不得伪装为真实运行数据。

## 4. 当前版本基线（2026-08-25）

npm 官方注册表与官方文档显示：

- React 当前稳定线为 19.2，当前补丁 19.2.8；
- Vite 当前补丁为 8.2.2，Vite 8 使用 Rolldown，要求 Node.js 20.19+ 或 22.12+；
- `@vitejs/plugin-react` 当前为 6.1.0；
- TypeScript 当前最新为 7.0.2，但 `@typescript/typescript6` 稳定线为 6.0.2；
- React Router 当前为 7.18.2，Data Mode 提供 loader、action、pending state 等路由数据能力；
- TanStack Query 当前为 5.102.3；
- Next.js 当前为 16.3.2；
- Vue 当前为 3.5.41；
- Vitest 当前为 4.1.11。

具体补丁版本应进入 lockfile；升级由类型检查、组件测试、端到端测试、构建和容器验证共同驱动，不能继续使用宽泛的 `^` 作为生产可复现性的唯一保障。

### 4.1 为什么首版不直接采用 TypeScript 7

TypeScript 7 是正式版，并非预览版；官方报告其原生 Go 实现可显著提升大型项目类型检查速度，也明确称其已可用于生产。但当前 7.0 不提供稳定的 TypeScript 编程 API，官方建议需要 API 的工具与 TypeScript 6 并行运行；Vue、MDX、Astro、Svelte 等嵌入式语言工具暂时仍需 TypeScript 6。

本次实测 npm peer 约束显示，当前 `typescript-eslint` 8.68.0 支持 `typescript >=4.8.4 <6.1.0`。若首版直接采用 TypeScript 7，就需要同时维护 TS7 编译器与 TS6 lint API，增加 CI、编辑器和问题定位复杂度，而当前 435 行 JavaScript 迁移项目没有性能收益证据支持这项复杂度。

因此首版采用 TypeScript 6.0.2，并清除 6.0 弃用项，为未来升级 TS7 做准备。只有在 ESLint、OpenAPI 生成器、测试和编辑器插件均声明支持、且完整门槛通过后，才单独升级到 TypeScript 7。

### 4.2 Vite 8 的升级边界

Vite 8 已是稳定支持线，但它把构建器从 Rollup/esbuild 统一切换为 Rolldown/Oxc，是一次真实的构建系统迁移。官方迁移说明列出了浏览器默认目标提升、`rollupOptions` 迁移、手工分块、插件 hook 和旧格式输出等差异。

当前 SmartLib `vite.config.js` 只有 React 插件与开发代理，没有自定义 Rollup 插件、手工分块或旧模块格式，因此迁移面较小。但仍不应把 TypeScript、路由拆分和 Vite 8 升级塞进同一次不可区分的变更：先在 Vite 7 完成严格类型和测试基线，再升级 Vite 8并比较构建产物、深链接、API 代理和浏览器端回归。

Vite 8 默认浏览器基线包括 Chrome 111、Edge 111、Firefox 114 和 Safari 16.4。确认后实施前须取得校内受管终端的浏览器版本；如果仍存在更旧设备，应显式制定支持矩阵和降级策略，不能等上线后由用户发现。

## 5. 候选路线

### A. React + TypeScript + Vite（推荐）

建议基线：

- React 19.2.x；
- TypeScript 6.0.2，`strict`，禁止新增隐式 `any`；
- Vite 8.2.x 与 `@vitejs/plugin-react` 6.1.x；
- React Router 7 Data Mode；
- TanStack Query 5 管理远端状态；
- 从已提交 OpenAPI 生成 TypeScript 类型与客户端；
- Vitest + Testing Library 做单元/组件测试，Playwright 做浏览器端到端测试；
- Nginx 静态部署并同源代理 `/api`，保持当前 FastAPI 权威边界。

适配 SmartLib 的原因：

1. 保留现有七个工作区、图标、样式和交互，迁移可以逐页完成；
2. 静态 Web 镜像无服务端会话，私有化部署、Compose 和未来 Kubernetes 扩容简单；
3. FastAPI 已是后端与身份/策略执行入口，没有必要再增加一个 Node BFF 才能访问领域能力；
4. React Router 的模式是递进的，当前采用 Data Mode，若未来个别路由确有 SSR/SSG 证据，可评估 Framework Mode 或独立公开门户；
5. React 生态可支持复杂网络可视化、工作台、桌面壳和无障碍组件，但具体图库仍需场景 POC。

主要风险与控制：

- Vite 只负责构建，不自动提供生产路由、数据缓存和测试规范；本决策同时冻结 Router、Query、契约生成和测试门槛，避免再次形成自组装脚手架；
- SPA 首屏和公开 SEO 弱于 SSR；校内工作台不以搜索引擎索引为目标，公开门户独立判断；
- 现有单文件组件若直接改后缀会产生大量类型错误；采用 `allowJs` 过渡但设置清零期限，按路由纵向迁移，最终运行态源文件全部进入严格 TypeScript；
- React Server Components 不进入首期校内 SPA，避免引入与 FastAPI 重叠的服务端数据层和额外安全补丁面。

### B. Next.js 16 App Router

适配点：

- SSR、SSG、流式渲染、Server Components、路由与代码分割集成完整；
- 公开内容门户、新闻、成果展示和搜索引擎收录场景强；
- 可以保留 React 组件资产，重写成本低于 Vue。

不作为校内平台默认路线的原因：

- 当前权威后端已经是 FastAPI；引入 Server Actions、Route Handlers 或服务器组件直连数据会形成第二能力层，必须额外禁止和治理；
- 动态 SSR 需要 Node 运行时、服务端容量、补丁、日志和故障处理，增加 Compose/Kubernetes 运行面；
- 若只做静态导出，Next 的主要优势不能充分兑现，React/Vite 更直接；
- Next 官方在 2026-08-26 安排针对 16.3/15.5 的关键安全更新，说明服务端 React 栈需要进入独立的快速补丁与回归制度；这不是否决 Next，而是实际运维成本。

适用条件：学校已确认同一应用必须同时承载大量公开可索引内容，并愿意维护 Node 服务端；否则建议把公开门户作为独立应用决策。

### C. Vue 3 + TypeScript + Vite

适配点：

- Vue 3 对 TypeScript、SFC、Composition API、路由和状态工具支持成熟；
- 官方脚手架以 Vite 为基础，部署拓扑可与当前保持一致；
- 若学校已有长期 Vue 3 团队、组件库和统一门户规范，组织收益可能超过代码迁移成本。

当前代价：

- 七个 React 工作区、JSX 组件和交互状态需要重写，主要只能复用 CSS、文案和信息架构；
- 图标组件、测试和组件规范需要整体切换；
- 迁移期间同时维护 React 与 Vue 会拖慢真实 API 接入，并不会改善后端能力复用。

适用条件：能够确认学校长期前端规范是 Vue 3，并有负责该平台的成熟 Vue 团队和可直接复用的组件资产。仅有“有人写过 Vue”不足以支持重构。

## 6. SmartLib 加权比较

评分只针对当前仓库和平台约束，5 为最匹配，不是框架通用排名。

| 维度 | 权重 | React/TS/Vite | Next.js | Vue/TS/Vite |
|---|---:|---:|---:|---:|
| 保留现有资产与增量迁移 | 25% | 5.0 | 4.0 | 2.0 |
| 长期类型与模块治理 | 20% | 4.5 | 4.5 | 4.5 |
| 与 FastAPI 权威边界一致 | 15% | 5.0 | 3.5 | 5.0 |
| 校内复杂工作台体验 | 15% | 4.5 | 4.5 | 4.5 |
| 私有化部署与运维简单度 | 10% | 5.0 | 3.0 | 5.0 |
| 公开内容、SEO 与预渲染 | 10% | 2.5 | 5.0 | 3.0 |
| 生态与人才可获得性 | 5% | 5.0 | 5.0 | 4.5 |
| 当前加权结果 | 100% | **4.58** | **4.10** | **3.78** |

结论会被两项组织事实改变：

- 学校已冻结 Vue 3 为统一技术规范并提供成熟团队/组件库：Vue 的组织收益可能超过重写成本；
- 校内工作台必须与公开 SEO 门户同应用、同路由、同发布单元运行：Next.js 得分会上升。

在这两项事实尚无证据时，React/TypeScript/Vite 是风险最低且最符合现有资产的路线。

## 7. 建议决策

建议确认：

> SmartLib 校内 Web 平台采用 React 19.2、TypeScript 6.0 和 Vite 8 主路线；使用 React Router 7 Data Mode 管理 URL、路由加载和权限边界，TanStack Query 管理服务端状态，前端客户端由平台 OpenAPI 生成；生产以 Nginx 静态镜像部署并同源代理 FastAPI。公开门户、小程序和原生客户端是独立渠道应用，共享能力契约与设计令牌，不强制共享 Web 组件。TypeScript 7 在工具链完整兼容后单独升级。若未来确认公开门户需要 SSR/SSG，再为 `apps/public-web` 单独评估 Next.js，不改写校内平台核心。

## 8. 确认后的首个开发任务

若确认路线 A，立即实施“Web 正式工程化基线”而不是继续新增演示页面：

1. 先在当前 Vite 7 上建立 TypeScript 6 严格门槛，再单独升级 Vite 8，隔离语言迁移与 Rolldown 构建迁移风险；
2. 建立严格 TypeScript、ESLint、格式、类型检查和生产构建门槛；
3. 引入 React Router Data Mode，将七个工作区变为可深链接路由；
4. 按 `app / routes / features / shared / generated` 拆分 435 行 `App.jsx`；
5. 从 `packages/api-contracts/openapi` 生成只读的 TypeScript API 客户端；
6. 用 TanStack Query 建立统一鉴权、错误、重试、缓存和失效策略；
7. 将“知识基础设施”真实 API 面板迁到生成客户端，并增加 loading/error/empty 权威状态；
8. 把 `src/data.js` 移入明确的 `fixtures/demo`，禁止生产路由直接导入；
9. 加入路由、API 状态、RLS 展示边界和关键交互的组件/端到端测试；
10. 保持当前 Nginx/Compose 拓扑，验证刷新深链接、Web→API、容器健康与回滚。

## 9. 项目负责人决定与实施结果

项目负责人于 2026-08-25 确认 React/TypeScript/Vite 主路线。实施已按 ADR-0004 完成首个工程化基线：先在 Vite 7 上完成 TypeScript 6、路由、生成客户端和测试，再独立升级 Vite 8。七个工作区深链接、生成客户端漂移检查、严格类型、lint、组件/架构测试、生产构建、Playwright 深链接、axe 无障碍、Nginx 同源 API 与 Compose 健康均已实测通过。

实现选择补充：`openapi-typescript` 7.13.0 的 peer 约束仍限定 TypeScript 5.x，因此未强制安装，改用明确支持 TypeScript 6 的 `@hey-api/openapi-ts` 0.99.0。其传递 YAML 解析依赖通过 `js-yaml` 4.3.1 override 闭合当前安全公告，最终 `npm audit` 为 0 项漏洞。ESLint 采用当前受支持的 10.0.1；由于 `eslint-plugin-jsx-a11y` 6.10.2 尚未声明 ESLint 10 兼容，无障碍门槛由真实浏览器中的 axe 4.11.1 承担。

如学校存在已冻结的 Vue 3 技术规范或必须同应用承载公开 SEO 门户，请在确认前提供该事实，结论将据此重算。

浏览器兼容不改变 React/Vue/Next 主路线判断，但会影响 Vite 8 的 `build.target`、测试矩阵和是否需要兼容构建。若校内存在不能升级的旧浏览器终端，也请一并说明。

ADR-0004 已生成并接受。其验收条件已完成：七个工作区均可通过 URL 深链接；路由层不直接导入 demo fixture；OpenAPI 生成客户端不可手工修改且有漂移检查；类型检查、测试和生产构建共同通过；Nginx 刷新深链接与同源 API 代理完成容器验证。
