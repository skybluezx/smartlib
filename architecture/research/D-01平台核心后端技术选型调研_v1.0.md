# D-01 平台核心后端技术选型调研 v1.0

- 状态：已决策
- 日期：2026-08-25
- 关联决策：D-01
- 调研建议：Java 25 LTS + Spring Boot 4.1 + Spring Modulith 2.1 平台核心
- 最终决定：Python 3.14 + FastAPI 平台核心主路线（ADR-0003）

## 1. 这项决策决定什么

平台核心是 PostgreSQL 权威状态之上的唯一业务能力层。它不是单纯给 Web 提供数据，也不是 AI 服务的外壳，而要长期承载：

- 对象、来源、证据、关系、画像、许可、审核、任务和审计的业务规则；
- 权威状态与 Outbox 事件的事务一致性；
- 身份上下文、用途、许可、风险和人工批准；
- 协议无关的能力目录；
- Channel API、Public API、Webhook、MCP、Skill 和 Agent 的共同领域语义；
- 模块边界、兼容策略、可观测性和未来服务拆分路径。

Python 数据处理、实体解析、检索实验、RAG、模型调用和评测可以独立演进，但不得绕过平台核心直接修改权威状态。

## 2. 已确认约束

1. 首版采用模块化单体，不提前拆成大量微服务。
2. PostgreSQL 18 是平台权威主库，Flyway 是唯一 schema migration 入口。
3. Web、Public API、MCP、Skill、Agent、小程序和客户端必须复用相同领域能力、授权和审计语义。
4. REST/OpenAPI 是首期同步契约；SSE 用于进度和流式回答；事件采用版本化 schema。
5. 平台核心必须在同一事务内写领域状态和 Outbox。
6. 搜索、图、向量和 AI 是适配器或可重建投影，不进入领域核心。
7. 业务代码不能依赖 bootstrap 数据库账号，也不能在启动时隐式改表。

## 3. 评价维度

| 维度 | 权重 | SmartLib 判断标准 |
|---|---:|---|
| 长期领域演进 | 25% | 模块边界可验证，复杂规则可维护，可按证据拆分 |
| 安全、许可与审计 | 20% | 身份上下文、方法级授权、事务、审计和拒绝路径完整 |
| 首版真实交付速度 | 20% | 能尽快让 Web 经 API 使用真实数据库，而非继续扩展 mock |
| 运维与人才可持续性 | 15% | 团队能调试、升级、监控和处理生产故障 |
| 多入口契约能力 | 10% | OpenAPI、事件、SDK、MCP 适配和兼容治理清晰 |
| 数据与 AI 协作 | 10% | 与 Python 工作进程边界清楚，任务和结果可追踪 |

## 4. 候选路线

### A. Java/Spring Modulith 平台核心 + Python/FastAPI 工作进程（推荐）

建议首版版本基线：

- Eclipse Temurin 25 LTS；
- Spring Boot 4.1.x；
- Spring Modulith 2.1.x；
- Maven Wrapper；
- Spring MVC、Spring Security、Spring JDBC/JdbcClient；
- 独立 Flyway migration，不启用 ORM 自动 DDL；
- Python/FastAPI 仅承担数据、检索、AI 和长任务工作进程。

适配 SmartLib 的原因：

- Spring Modulith 能验证模块无循环依赖、只通过公开接口访问模块，并支持单模块集成测试、模块文档和运行时结构校验；
- Spring 事务、安全、OAuth2/OIDC、JDBC、Actuator、Micrometer/OpenTelemetry 与私有化运维生态完整；
- 编译期类型和包可见性适合保护长期领域模型，避免各入口直接复用数据库实体；
- 模块事件可先在单体内保持清晰边界，外部投影仍使用已建立的 SmartLib Outbox；
- Python 保留在真正需要其数据和 AI 生态的区域，两种语言通过 OpenAPI、任务和事件契约协作。

风险与控制：

- 初始代码和构建复杂度高于 FastAPI；用单模块 Maven 工程、Maven Wrapper 和少量依赖控制首版体量；
- Java + Python 是双语言栈；首版先交付 Java 平台核心，Python 工作进程只在出现第一个真实数据/AI 任务时启用；
- Spring 生态容易因“全家桶”膨胀；首版不引入 Spring Cloud、服务注册中心、GraphQL 和消息总线；
- Spring Modulith 的事件外发不替代现有 Outbox 表，避免形成两套权威事件发布机制；
- JDK 选择 Eclipse Temurin 等 OpenJDK 发行版，生产支持和许可由学校另行确认。

### B. Python/FastAPI 同时承担平台核心和数据/AI 工作进程

适配点：

- FastAPI 原生围绕 OpenAPI、JSON Schema、Pydantic、依赖注入和标准安全模式，接口交付速度快；
- 领域 API、数据处理和 AI 开发共享 Python 类型与工具，早期团队切换成本低；
- 对小团队、Python 人才占绝对多数、近期以数据接入和 AI 示范为主的项目非常有效。

主要风险：

- FastAPI 提供 Web/API 基础，但不提供 Spring Modulith 同类的领域模块结构验证、可靠模块事件登记和模块级架构测试，需要自行制定并持续执行；
- ORM、同步/异步数据库访问、后台任务、事件、授权和依赖注入的组合选择更多，团队规范不足时容易产生多种并存实现；
- Python 类型检查不是运行构建的天然强制门槛，必须把 `mypy/pyright`、lint、依赖边界和契约测试设为 CI 硬门槛；
- 如果同一进程加载大型模型，多 worker 会重复占用内存；平台核心与模型运行仍应分开部署。

适用条件：未来两年无法保证任何 Spring 维护能力，且 Python 开发/运维能力占团队 70% 以上。

### C. TypeScript/NestJS 平台核心 + Python 工作进程

适配点：

- Web 与平台核心共享 TypeScript 人才、类型工具、包管理和部分契约模型；
- NestJS 提供模块、依赖注入、守卫、拦截器、OpenAPI、SSE、队列与多种微服务传输适配；
- 首版开发体验和接口速度较好，适合成熟全栈 TypeScript 团队。

主要风险：

- 装饰器模块能组织代码，但缺少 Spring Modulith 同级的模块依赖验证、模块级运行观测和恢复型事件发布体系，需要 ArchUnitTS/ESLint 规则与测试补齐；
- 事务、Unit of Work、Outbox 和数据库类型安全依赖额外 ORM/query builder 选择，容易把 D-01 与数据访问工具选型纠缠；
- CPU 密集的数据和 AI 工作仍需 Python，最终仍是双语言；
- npm 依赖和框架主版本升级需要更严格的供应链锁定与审计。

适用条件：平台团队以 TypeScript 为主，且具备后端安全、事务和生产运维经验，而不只是前端经验。

### D. ASP.NET Core + Python（组织能力候选）

如果学校已有成熟 Microsoft/.NET 团队、统一身份和部署规范，ASP.NET Core 是强候选，具备类型、安全、OpenAPI、性能和长期支持优势。但当前 SmartLib 材料没有 .NET 团队或既有平台证据，因此不扩展为默认路线；出现该组织事实时应补充 POC，而不是直接排除。

### E. Go + Python（特定团队候选）

Go 适合轻量、高并发服务和单文件部署，但 SmartLib 首期瓶颈并非网关吞吐，而是领域治理、许可、事务、证据和审计。除非团队已有成熟 Go 领域服务框架与运维经验，否则会增加自建基础设施代码，不作为默认路线。

## 5. 当前版本与生命周期判断

- Java 25 已被列为 LTS；Eclipse Temurin 25 提供免费、跨平台 OpenJDK 构建，并计划至少维护到 2031 年；
- Spring Boot 4.1.1 要求 Java 17 以上，并支持到 Java 26；
- Spring Modulith 2.1.0 是当前稳定版，提供模块验证、集成测试、模块观测、文档和事件发布生命周期；
- 因此若选择路线 A，不再以旧方案中的 Java 21 作为新项目默认基线，而采用 Temurin 25 LTS；
- 具体补丁版本应固定在构建文件与容器摘要中，升级由依赖测试和恢复验证驱动。

## 6. 面向 SmartLib 的比较

以下分值是当前架构判断，不是语言或框架通用排名。5 为最匹配。

| 维度 | Java/Spring + Python | Python/FastAPI | TS/NestJS + Python |
|---|---:|---:|---:|
| 长期领域演进 | 5 | 3 | 4 |
| 安全、许可与审计 | 5 | 3.5 | 4 |
| 首版真实交付速度 | 3.5 | 5 | 4.5 |
| 运维与人才可持续性 | 3，待团队核验 | 4，待团队核验 | 4，待团队核验 |
| 多入口契约能力 | 5 | 4.5 | 4.5 |
| 数据与 AI 协作 | 4.5 | 5 | 4.5 |
| 当前加权结果 | **4.35** | **4.00** | **4.20** |

团队能力会改变结论：

- 至少有 1 名能够长期维护 Spring Boot 的核心开发者：路线 A 保持推荐；
- Python 人员占 70% 以上且没有 Java 运维能力：路线 B 的实际得分将超过 A；
- 前后端均由成熟 TypeScript 后端团队维护：路线 C 可接近或超过 A；
- 只有前端 TypeScript 经验，不等同于具备 NestJS 平台核心能力。

## 7. 建议与最终决策

建议确认：

> SmartLib 平台核心采用 Eclipse Temurin 25 LTS、Spring Boot 4.1 和 Spring Modulith 2.1，以模块化单体承载权威领域状态、事务、许可、审核、任务与审计；Python/FastAPI 作为独立数据与 AI 工作进程。所有入口通过版本化能力与 API 契约使用平台核心，不直接访问 PostgreSQL。首版使用 Maven Wrapper、Spring JDBC，不引入 Spring Cloud、微服务注册中心或应用自动 DDL。

这个建议成立的必要组织条件是：项目能够指定至少一名长期维护 Spring Boot 的开发者。若该条件明确不成立，应选择 Python/FastAPI 主路线，不应为了“企业级”标签引入无人维护的 Java 栈。

项目负责人于 2026-08-25 确认采用 Python/FastAPI 主路线。该决定覆盖调研阶段的默认建议，但保留比较结论作为风险依据。实施时以模块依赖测试、严格类型和 lint、事务集成测试及版本化契约作为强制补偿措施，详见 ADR-0003。

## 8. 确认后的首个开发任务

按已确认的 Python/FastAPI 路线，立即实施一个纵向最小切片：

1. 建立 `apps/platform-api` 的 Python 3.14/FastAPI 工程；
2. 建立 `foundation`、`source`、`knowledge`、`operations`、`audit` 五个首批模块边界；
3. 用架构测试强制无循环依赖和只通过模块公开接口访问；
4. 使用独立应用数据库角色接入 PostgreSQL，不使用 bootstrap 账号；
5. 建立 `/api/v1/sources`、`/api/v1/objects`、`/api/v1/objects/{id}`、`/api/v1/jobs/{id}` 首批接口；
6. 在同一事务写入 `knowledge_object` 与 `outbox_event`；
7. 输出版本化 OpenAPI，并建立协议无关能力目录首版；
8. 加入健康检查、结构化错误、`trace_id`、容器镜像和 Compose；
9. 让 Web 的一个页面改为调用真实 API，保留其余未迁移页面的明确演示标记；
10. 验证 API、数据库、RLS、Outbox、模块边界和 Web 真实链路。
