# D-06 数据接入与连接器框架技术选型调研 v1.0

- 状态：调研完成；项目负责人决定 Demo 阶段暂缓，真实数据接入前重新决策
- 日期：2026-08-26
- 关联决策：D-06、ADR-0007（提议）
- 原建议结论：SmartLib 自有连接器契约与 Python SDK 作为长期稳定边界；首批正式 API/受控文件连接器由平台原生 worker 实现；Apache SeaTunnel 2.3.13 + Zeta 作为数据库、文件、批量与 CDC 数据移动 POC 副执行器；Airbyte 与 NiFi 暂不进入首轮

> 2026-08-26 决定：当前优先开发使用明确标记模拟数据的 Demo，D-06 暂缓。本文保留为真实数据接入前的重新评估基线，不授权当前部署 SeaTunnel。

## 1. 这项决策真正解决什么

D-06 不是选择一个“能搬数据”的产品，而是确定 SmartLib 如何持续、合规地接入学校业务系统、图书馆电子资源、机构知识库、受控文件和外部学术接口，并把每次接入变成可追溯、可重放、可审计的知识形成过程。

连接器必须处理产品工具通常不了解的 SmartLib 语义：

- 数据来源、责任部门、授权状态和异常联系人；
- 数据集、字段、更新方式、许可用途、保存期限和展示边界；
- 全量快照、增量游标、CDC 位点、文件清单和内容校验和；
- 每个原始记录的外部标识、源版本、事件时间和接收时间；
- 重复交付、模式变化、部分失败、撤回、删除和重新同步；
- 从原始批次到规范对象、关系、证据、搜索和图投影的完整追溯。

因此第三方工具只能承担执行或数据移动，不能成为 SmartLib 的数据源目录、许可模型、权威对象模型或公共能力契约。

## 2. 已核实的当前系统状态

当前工程已经有：

- `source_system` 数据源登记；
- PostgreSQL RLS、审计事件和通用 `async_job`；
- 规范对象、关系、证据及搜索/图投影 Outbox；
- Python/FastAPI 模块化平台核心与统一能力目录。

当前仍缺少：

- 连接器定义、版本和能力声明；
- 数据源实例与凭据引用；
- 接入运行、分区、检查点、重试与取消语义；
- 接入清单、记录信封、模式版本、校验和与许可快照；
- 原始接入区到规范模型的发布门；
- 连接器一致性测试套件；
- 首批 1–2 个获授权真实源、数据量、日增量和时效要求。

这些缺口说明：即使引入 SeaTunnel、Airbyte 或 NiFi，也必须先建设 SmartLib 自己的接入控制面。

## 3. 冻结的产品无关架构

### 3.1 控制面与执行面分离

SmartLib 控制面由 FastAPI + PostgreSQL 承担：

- 登记数据源、连接器定义、实例、能力与版本；
- 保存非敏感配置和密钥引用，不保存明文密钥；
- 创建接入运行、分区任务和审计事件；
- 接收运行心跳、进度、错误、检查点和清单；
- 校验许可、质量和模式后才允许发布到规范模型。

执行面可以是：

1. 平台原生 Python 连接器 worker；
2. SeaTunnel Zeta 作业适配器；
3. 未来经同一验收集批准的其他执行器。

执行器不得直接把外部数据写成 SmartLib 权威对象。它只能提交版本化接入信封或写入受控落地区，由平台在同一治理规则下归一化、核验和发布。

### 3.2 统一连接器协议

首版稳定接口：

- `probe()`：验证网络、身份、授权、配额和源版本；
- `discover()`：返回数据集、字段、主键、增量能力和模式指纹；
- `snapshot()`：生成有界快照分区；
- `changes()`：从平台签发的检查点读取增量或 CDC；
- `fetch_object()`：按许可受控获取文件或内容；
- `health()`：返回连接、凭据到期、配额、限流和最近成功状态；
- `manifest()`：生成批次、记录数、范围、校验和、许可快照和错误摘要。

连接器输出统一 `IngestionEnvelope`，至少包含：

- `source_system_id`、`connector_instance_id`、`run_id`；
- `dataset_key`、`external_id`、`source_version`；
- `operation`（upsert/delete/tombstone）；
- `occurred_at`、`observed_at`；
- `schema_version`、`payload_checksum`；
- `visibility`、`license_tags`、`purpose_tags`；
- `payload` 或受控对象引用；
- `checkpoint_candidate`。

### 3.3 交付语义

SmartLib 的跨系统承诺采用“至少一次交付 + 规范层幂等提交 + 可核对清单”，不把某个引擎的 Exactly-once 宣传扩大为端到端保证。

- 幂等键由来源、数据集、外部 ID、源版本和操作共同确定；
- 检查点只有在落地区持久化并完成清单核对后才能推进；
- 规范对象发布失败不能丢失原始接入批次；
- 重跑同一批次不得产生重复对象、关系或证据；
- 删除和撤回必须使用显式 tombstone，不以“本批未出现”直接推断删除；
- 模式漂移默认隔离并等待审核，不能静默丢字段或改变类型。

## 4. 候选方案

### A. SmartLib 自有连接器 SDK（必须建设，推荐主控制面）

适合首批正式 API、受控 CSV/JSON/XML/Excel、机构知识库和具有特殊许可语义的电子资源连接器。

优势：

- 与已确认的 Python/FastAPI 路线一致；
- 可以把许可、来源、批次、字段映射和证据语义放在类型契约中；
- 代码、测试和配置可正常审查；
- 首批 1–2 个特定连接器依赖最少。

风险：

- 不能长期重复自研通用 JDBC、CDC、FTP/SFTP 和对象存储数据移动能力；
- 必须从第一天提供契约测试、检查点、限流、重试和密钥边界，否则会退化为零散脚本。

结论：它不是与 SeaTunnel 二选一，而是 SmartLib 不可替代的稳定边界。

### B. Apache SeaTunnel 2.3.13 + Zeta（推荐 POC 数据移动执行器）

官方 2.3.13 文档与发布记录显示：

- Zeta 是新项目和数据同步/CDC 的推荐默认引擎；
- 支持批、流、CDC、检查点、模式演进和多表同步；
- 2.3.13 源连接器覆盖 JDBC、PostgreSQL/MySQL/Oracle/SQL Server CDC、HTTP、SFTP、S3/OSS/OBS、本地文件、Kafka、RabbitMQ 等；
- REST API v2 能提交/管理作业并读取检查点历史；
- 生产恢复需要把 checkpoint 和 IMap/MapStore 状态放到共享或对象存储，不能只依赖容器本地盘；
- 自定义高性能 connector 主要使用 Java SPI，开发和打包成本高于平台原生 Python 连接器。

适合 SmartLib 的角色：

- 大批量 JDBC/文件搬运；
- 获得正式源端权限后的 CDC；
- 第二批以后重复出现的标准数据移动模式；
- 作为 `ConnectorExecutorPort` 的一种适配器，而不是业务控制面。

必须验证：

- 具体连接器在 2.3.13 + Zeta 下的语义，不以总功能表代替逐连接器证据；
- JDBC 驱动与 CDC 插件制品、许可证和漏洞；
- 模式漂移、快照到增量切换、断点恢复、删除事件与乱序；
- REST API 的认证、网络隔离、密钥注入和日志脱敏；
- 作业取消、集群全停、升级和状态恢复；
- 对 SmartLib 接入信封/落地区的适配成本。

### C. Airbyte 2.x（SaaS/API 长尾候选，首轮不推荐）

官方仓库当前宣传 600+ 连接器，并提供无代码 Connector Builder、低代码 CDK 和 Python CDK，对通用 SaaS/API 接入具有明显优势。

当前不作为首轮主线的原因：

- Airbyte 主仓库和连接器采用 Elastic License 2.0，协议为 MIT；学校内部自托管通常可用，但不属于 Apache 2.0 路线，仍需法务和采购边界核验；
- Self-Managed Core 与 Enterprise 在 SSO、RBAC、多租户、数据脱敏、企业连接器和支持上存在权益差异；
- Marketplace 连接器无生产 SLA，归档连接器可能停止维护；
- Airbyte 的 source/destination/connection 模型仍不能表达 SmartLib 许可、证据、发布门和知识对象语义；
- 当前首批源系统尚未明确，无法证明 600+ 连接器对学校本地系统和国内电子资源有实际覆盖价值。

触发条件：首批真实源中出现多个 Airbyte 官方稳定连接器覆盖的 SaaS/API，且运维、许可和安全收益优于 SDK/SeaTunnel 时，用同一验收集加入。

### D. Apache NiFi 2.10（边缘路由与可视运维候选，首轮不推荐）

NiFi 2.10 提供可视化流、持久队列、背压、数据沿途 provenance、细粒度授权和集群能力，适合复杂文件路由、边缘采集和运维人员实时观察数据流。

当前不作为首轮主线的原因：

- 大量画布式流程容易把业务映射和治理规则散落在处理器配置中；
- 流定义、参数、密钥和环境差异需要额外建立 GitOps 规范；
- NiFi Registry 已于 2026 年 2 月宣布弃用并计划在 NiFi 3.0 移除，NiFi 2 应采用 Git-based Flow Registry Client；
- 与当前 Python 团队、模块化 API、数据库任务控制面的重叠较大；
- SmartLib 目前没有边缘节点、超大文件路由或大量运维人员画布编排的已证需求。

触发条件：学校已有受支持 NiFi 平台，或真实场景证明需要边缘路由、持久缓冲、背压和 provenance UI 时加入。

## 5. 暂定比较矩阵

| 维度 | SmartLib SDK | SeaTunnel 2.3.13 | Airbyte 2.x | NiFi 2.10 |
|---|---|---|---|---|
| 首轮角色 | **稳定契约与原生执行器** | **标准搬运/CDC POC** | 条件候选 | 条件候选 |
| SmartLib 许可/证据语义 | 强 | 需适配 | 需适配 | 需适配 |
| 正式 API/特殊资源 | 强 | HTTP 能力需逐源验证 | SaaS/API 生态强 | 可组合但配置复杂 |
| JDBC/文件/CDC | 需自建，不经济 | 强 | 强，按连接器支持等级 | 强，按处理器组合 |
| Python 团队匹配 | 强 | 运维可用，自定义 connector 偏 Java | Python CDK 较好 | 自定义扩展偏 Java |
| 代码审查/测试 | 强 | 作业配置可版本化 | 配置/API 可管理 | 必须建立 Flow GitOps |
| 运行可视化 | 需建设 | 中 | 强 | 强 |
| 许可证 | 项目自有 | Apache 2.0 | ELv2，协议 MIT | Apache 2.0 |
| 当前引入成本 | 低到中 | 中 | 中高 | 中高 |
| 当前主要风险 | 长期重复造轮子 | 状态存储、插件和运维 | 许可/权益与组件复杂度 | 画布治理和平台重叠 |

## 6. 原推荐决策（当前已延后）

建议项目负责人确认：

> SmartLib 采用“自有连接器契约与 Python SDK + Apache SeaTunnel 2.3.13/Zeta POC”主路线。控制面、许可、批次、清单、检查点和发布门由 SmartLib FastAPI/PostgreSQL 掌握；首批正式 API/受控文件连接器由原生 Python worker 实现；SeaTunnel 仅作为可替换的数据移动执行器，用获授权真实源验证 JDBC/文件/CDC。Airbyte 和 NiFi 暂不进入首轮，分别由 SaaS/API 长尾和边缘路由/既有校级平台证据触发。

这一路线避免两个极端：既不把所有数据移动都长期自研，也不让第三方工具反向定义 SmartLib 的知识与许可模型。

## 7. 仍需负责人/学校补充的事实

- 首批 1–2 个真实源的系统名称、责任部门和接口负责人；
- 接入方式：正式 REST/GraphQL/OAI-PMH/SRU、受控文件、数据交换平台、只读库或 CDC；
- 样本模式、主键、更新时间字段、删除语义、全量和日增量；
- 凭据机制、网络位置、限流、维护窗口和故障联系人；
- 数据授权用途、保存期限、可展示字段、TDM/模型处理和出域边界；
- 学校是否已有 SeaTunnel、Flink、NiFi、Airbyte 或统一数据交换平台；
- 对 Java 数据工程组件的运维能力和正式制品仓库要求。

首批数据源应使用《D-06 首批真实数据源准入与信息采集表 v1.0》逐源登记；授权、安全、稳定标识和追溯任一准入门未通过时，不进入真实数据 POC。
