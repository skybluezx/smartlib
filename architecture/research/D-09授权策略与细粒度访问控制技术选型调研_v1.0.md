# D-09 授权策略与细粒度访问控制技术选型调研 v1.0

- 状态：调研已完成；项目负责人决定首次 Demo 阶段延后实施
- 日期：2026-08-26
- 范围：应用授权、许可用途、数据过滤与数据库纵深防护；认证由 D-08 处理

## 1. 当前阶段决定与目标建议

项目负责人于 2026-08-26 决定：当前首次 Demo 展示阶段不新增 `PolicyDecisionPort`、OPA 或 OpenFGA。已有 RLS、许可默认拒绝、投影过滤、service 后验和审计继续生效，不因延后而删除或放宽。本调研保留为进入真实用户/数据、多接口真实开放或复杂许可阶段时的决策输入。

建议采用 **SmartLib `PolicyDecisionPort` + PostgreSQL 权威策略数据与 RLS 当前主路线，OPA POC 延后到跨服务/策略独立发布阶段，OpenFGA POC 延后到关系授权规模阶段**。

这不是“无授权”或把策略永久写死在 Python：

1. 当前 Demo 继续执行真实的可见性、所有者、许可状态、用途、到期、证据和 RLS 判断；
2. 将散落在 SQL、搜索、图和治理 helper 中的判断收敛为稳定、产品中立的 `PolicyDecisionPort` 输入/输出合同；
3. 首期由进程内 SmartLib policy adapter 执行，策略事实来自 PostgreSQL 权威域，并保留结构化决定、原因、义务和策略版本；
4. PostgreSQL RLS 仍是最后一道数据边界，不替代应用许可策略，也不由外部引擎绕过；
5. OPA 和 OpenFGA 分别保留适配器边界与触发条件，未来接入不改变业务 API、多入口语义或数据库主键。

## 2. 当前系统已具备什么

当前不是“空白授权”状态：

- PostgreSQL RLS 使用事务级 `smartlib.actor_id` 隔离对象、关系、证据、任务、投影和治理资产；
- 应用数据库角色无 `BYPASSRLS`，表和审计默认不授予 `PUBLIC`；
- 搜索与图适配器先过滤，service 层再校验返回节点/边/命中，发现越界即整体拒绝；
- `license_grant` 已包含状态、有效期、允许内容、允许/禁止用途；未知、待审、暂停、过期与未来许可均不允许；
- 审计是 append-only，已能记录 actor、action、resource、decision、trace 和 policy version；
- synthetic seed 包含公共、校内、私有与许可拒绝哨兵。

但仍有明显缺口：

- `public OR created_by = actor` 逻辑在 SQL、搜索和图服务中重复；
- `campus` 当前与真实组织身份没有可验证关系，D-08 延后期间只能是 Demo 语义；
- 许可 helper 只判断状态/时间，尚未统一计算 action、purpose、content、principal、network、model use 和 obligations；
- 没有统一 `PolicyRequest/PolicyDecision`、原因码、义务、策略版本和 denied 审计；
- 列表/搜索/分面/路径的“授权过滤”与单对象 allow/deny 尚未形成同一契约；
- OpenSearch/HugeGraph 投影的撤权传播与应用策略版本尚未统一验收。

因此 D-09 的当前价值是把已有真实防护变成可演进的正式平台能力，而不是立即增加一个策略容器。

## 3. 候选路线比较

| 路线 | 决策模型 | 当前优势 | 当前代价/风险 | 适合 SmartLib 的阶段 |
|---|---|---|---|---|
| A. SmartLib policy core + PostgreSQL/RLS | Python 领域策略 + 权威关系/许可数据 + DB RLS | 与现有事务、许可、证据、投影和测试直接衔接；组件最少；能先固定端口 | 若不强制模块/版本/测试，易重新散落；跨语言复用较弱 | **当前 Demo/模块化单体主路线** |
| B. OPA/Rego + PostgreSQL/RLS | 无状态策略引擎评估结构化 input，PG 提供事实与防线 | ABAC、用途、上下文和结构化 obligations 表达强；策略可独立测试/发布；跨服务统一 | 新增 Rego 能力、bundle/decision log/HA/升级；动态许可事实如何注入和一致性复杂；OPA 不保存权威关系 | **跨服务和独立策略发布触发后 POC** |
| C. OpenFGA + PostgreSQL/RLS | 授权模型 + user-relation-object tuples | 组织/项目/文档分享、父子继承、多跳关系和 `ListObjects` 强；适合大规模 ReBAC | 新增关系副本和一致性；许可用途/合同/模型外发仍需应用或策略引擎；不是 RLS | **共享/继承/反向查询规模触发后 POC** |
| D. OPA + OpenFGA + PostgreSQL | OPA 处理 ABAC，OpenFGA 处理 ReBAC，PG 权威/RLS | 理论覆盖最全 | 三套决定/数据面、两类策略语言、同步与故障组合过重 | 不进入当前首轮 |
| E. Casbin 等嵌入式通用库 | ACL/RBAC/ABAC 配置模型 | 进程内、入门快、模型多 | 仍需另建策略事实/适配层；对 SmartLib 许可义务和多引擎演进的增益有限 | 不作为首选，可在特殊团队约束下复评 |

OPA 官方定义是通用、无领域状态的策略决策引擎：应用提供结构化 input，OPA 返回任意结构化决定；策略与执行点分离（[OPA Introduction](https://www.openpolicyagent.org/docs)）。OPA 自身不应成为许可/组织事实权威，官方外部数据指南也明确需要通过 input、bundle、push 或按需读取处理外部事实，各有新鲜度、内存、可用性和耦合权衡（[OPA External Data](https://www.openpolicyagent.org/docs/external-data)）。

OpenFGA 的核心是授权模型与关系 tuple，擅长回答“用户 U 是否对对象 O 有关系 R”以及 `ListObjects` 等反向查询；其 conditions 可补充部分属性判断（[OpenFGA Concepts](https://openfga.dev/docs/concepts)、[Relationship Queries](https://openfga.dev/docs/interacting/relationship-queries)）。官方比较也明确区分无状态 policy engine 与持久化 relationship engine：前者适合请求时属性，后者适合共享、层级、成员关系和反向查询（[Policy Engines vs Relationship Engines](https://openfga.dev/docs/learn/policy-engine)）。

## 4. 不可混淆的四层职责

| 层 | 回答的问题 | 权威数据 | 当前/目标实现 |
|---|---|---|---|
| 认证 D-08 | 调用者是谁 | 学校 IdP + SmartLib principal mapping | Demo 已延后，当前仅 synthetic actor |
| 应用授权 D-09 | 主体能否在此用途下执行动作；有什么义务 | 角色/关系/许可/资源属性/上下文 | `PolicyDecisionPort` |
| 数据范围过滤 | 哪些对象/行/搜索命中/图路径可以进入候选集 | 与应用策略一致的可查询事实 | SQL/RLS + 投影过滤 + service 后验 |
| 数据库纵深防护 | 即使应用出错，哪些行仍不能读写 | PostgreSQL 权威表和事务主体 | PostgreSQL RLS |

RLS 不能判断所有业务许可和外部模型用途；OPA/OpenFGA 也不能自动保护绕过它们的直接 SQL。任何路线都必须同时定义决定点（PDP）、执行点（PEP）、过滤、审计和故障策略。

## 5. 产品中立策略合同

### 5.1 输入

```text
subject     actor_id, principal_type, roles, affiliations, delegation
action      标准动作词，如 view_metadata / create_embedding / export
resource    type, id, owner, visibility, policy_tags, license_refs, version
context     purpose, channel, network_zone, time, model_destination, trace_id
```

D-08 延后期间只有 synthetic actor/role 可用，必须在 UI 和审计中保持 Demo 标记。客户端提交的 role、network、license 或 owner 不能直接成为可信事实；由平台从数据库和受信上下文装配。

### 5.2 输出

```text
decision_id
effect          allow | deny | approval_required
reason_codes    稳定机器可读列表
obligations     redact, excerpt_limit, watermark, audit, prohibit_external_model...
policy_version
facts_version
expires_at      可选，仅表示决定缓存边界
```

没有匹配规则、事实缺失、策略不可用或关系冲突默认 `deny`。`approval_required` 不是 allow，必须进入 D-10 工作流或明确人工批准后重新判定。

## 6. 当前首期应收敛的策略

1. 对象/资产可见性：public、campus、restricted、private；
2. 所有者/创建者读写边界；
3. 电子资源许可动作词表与用途；
4. 生效时间、暂停、到期、待审与未知默认拒绝；
5. 证据正文、摘要、引用和导出的不同义务；
6. 搜索命中、分面计数、图节点/边/路径和问答上下文零泄漏；
7. 外部模型、向量化、TDM、批量下载和再发布；
8. 管理写操作与人工批准；
9. synthetic Demo 主体和数据不能升级为真实权限事实；
10. allow、deny、approval_required 均可追踪到策略/事实版本。

## 7. OPA 触发条件与边界

满足以下任一组合时启动 OPA POC：

- 两个以上独立部署的服务或语言必须执行同一套属性/用途策略；
- 合规/图书馆策略人员需要独立于应用发布审核和发布策略；
- 规则组合、义务或解释已明显超出可维护的 Python policy core；
- 需要把相同规则用于 API、数据管道、Agent Gateway 或基础设施入口；
- 有明确 policy bundle、签名、回滚、decision log、敏感字段脱敏和 HA 运维责任。

OPA POC 只实现 `PolicyDecisionPort` adapter；PostgreSQL 仍保存许可、对象和组织事实。禁止每次 Rego 决定随意 HTTP 拉取数据库事实；必须先选择并验证 input/bundle/push 的一致性策略。OPA 决策日志可能包含敏感 input，官方提供 masking 机制，因此日志脱敏是准入门而非可选项（[OPA Decision Logs](https://www.openpolicyagent.org/docs/management-decision-logs)）。

## 8. OpenFGA 触发条件与边界

满足以下任一组合时启动 OpenFGA POC：

- 项目、团队、机构、文件夹/集合、文档/数据集出现多层继承与共享；
- 需要高效回答“某用户可见的全部对象”或“哪些人能访问此对象”；
- 关系 tuple 数量和变化频率已使 PostgreSQL 递归/连接难以满足 SLO；
- 撤权传播、关系一致性、模型迁移和反向查询有真实规模测试集。

OpenFGA 不保存合同许可、证据内容或完整资源事实。若接入，它只成为关系授权投影；SmartLib PostgreSQL 仍是组织/项目/资源关系的业务权威，并需要 outbox/投影版本、重放、对账、撤权和故障时默认拒绝机制。

## 9. 恢复 D-09 后的建议实施范围

在 D-09 确认后，当前 Demo 只实施：

1. `policy` 模块和 `PolicyDecisionPort`；
2. 版本化动作、输入、决定、原因码、义务合同；
3. in-process adapter，读取调用方已从 PostgreSQL取得的最小权威事实；
4. 将治理许可 helper、搜索/图后验和新接口逐步迁到统一策略合同；
5. denied/approval_required append-only 审计；
6. 数据库 RLS、投影前过滤、service 后验三层一致性测试；
7. OPA/OpenFGA adapter contract tests，但不部署两个运行时。

这能让 Demo 展示“为什么允许/拒绝、依据哪条许可、需要什么处理义务”，同时保留未来外部策略引擎的替换路径。
