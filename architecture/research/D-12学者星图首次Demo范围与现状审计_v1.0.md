# D-12 学者星图首次 Demo 范围与现状审计 v1.0

- 状态：范围已确认；SG-01、SG-02 已完成，SG-03 待启动
- 日期：2026-08-26
- 范围：首次 Demo 的学者星图展示价值链；不把学者星图等同于 SmartLib 全平台

## 1. 结论先行

建议首次 Demo 只贯通一条 **“发现学者 → 事实画像 → 成果/项目/方向 → 合作网络 → 关系依据与来源追溯”** 的真实平台链路。

“真实平台链路”指版本化 synthetic 数据通过 PostgreSQL 权威模型、RLS、证据与 Outbox，进入搜索/图投影和 FastAPI 公共能力，再由 React 页面读取；不代表已经接入学校真实系统或真实个人数据。

首次 Demo 不追求七类应用、六维画像全量指标、人才评价排名、任务画像、AI 推荐、报告生成、纠错审批或真实异步任务。它们保留在最终系统架构中，但不进入本批开发。

## 2. 既有产品方案给出的长期边界

《学者星图 ScholarGraph 产品建设方案》把学者星图定义为高校科研人才数据画像与智能洞察平台，并明确了三层画像：

| 层次 | 长期含义 | 首次 Demo 处理 |
|---|---|---|
| 事实画像 | 身份、机构、职称、论文、项目、专利、获奖等可核验事实 | **纳入**，只展示已有 synthetic 事实及来源 |
| 分析画像 | 基于事实形成的指标、标签、趋势和比较结果 | **有限纳入**，只做可由当前事实直接计算的数量、研究方向和合作特征 |
| 任务画像 | 针对引进、评价、培养等具体任务形成的综合分析 | **不纳入**，避免把演示规则误作正式管理判断 |

长期六维画像仍为基本信息、科研产出、学术影响、研究方向、合作网络和发展变化。首次 Demo 只对基本信息、科研产出、研究方向和合作网络形成真实切片；学术影响与发展潜力仅保留产品位置，不展示无真实计算依据的数值。

## 3. 当前工程事实

### 已完成的可复用底座

- React/TypeScript/Vite 独立 `/scholars` 路由和现有视觉原型；
- FastAPI 知识对象、搜索、图邻域、有限路径、关系解释和来源追溯接口；
- PostgreSQL 18 规范对象、来源引用、证据、关系断言、RLS、审计与 Outbox；
- OpenSearch 3.8 POC 检索投影和 PostgreSQL 搜索基线；
- HugeGraph 1.7 图投影和 PostgreSQL 图查询基线；
- 协议无关能力目录、版本化 OpenAPI 和生成式 TypeScript 客户端。

### SG-02 启动前断点快照

- `/scholars` 的学者、指标和证据全部来自 `apps/web/src/fixtures/demo/data.ts`；
- 学者搜索是浏览器数组过滤，没有调用统一搜索；
- 学者详情、六维画像、成果数、项目数、合作者数和完整度是前端固定值；
- “研究方向证据”与证据抽屉是固定文本，没有关联 PostgreSQL `evidence_record`；
- 当前页面没有呈现真实关系网络，也没有调用关系解释；
- “新建比较”“申请纠错”“导出来源清单”等按钮只有提示或无行为；
- 现有通用对象/图 API 是底座能力，但没有面向学者场景的稳定读模型；
- 当前 governance synthetic seed 没有写入学者、成果、项目和学者关系数据。

因此，当前学者星图是视觉与交互原型，不是最终系统的首个可运行学者模块。

## 4. 首次 Demo 推荐价值链

### 场景 A：人才发现

用户可按姓名、院系和研究方向搜索 synthetic 学者，结果来自公共 API。搜索结果展示 Scholar ID、院系、职称、主研究方向和 synthetic 标识，不显示没有来源的排名。

### 场景 B：事实画像

选择学者后展示：基本身份、组织归属、研究方向、代表成果、参与项目和由当前可见事实计算的成果/项目/合作者数量。每项内容保留对象版本、更新时间和事实/分析类别。

### 场景 C：合作与知识网络

以当前学者为根节点展示学者—成果—项目—研究方向—机构关系；可切换关系类别，选择合作者或成果继续查看。前端只调用受限公共能力，不提交 Cypher。

### 场景 D：证据与来源追溯

点击研究方向或合作关系，可查看关系的 `fact_class`、置信度、审核状态、证据 ID、来源系统、观察时间和 synthetic 数据集版本。未知或无可见证据时明确显示“暂无可见依据”，不补造说明。

### 推荐演示叙事

```text
从一个研究主题找到校内候选学者
  → 打开一位学者的事实画像
  → 查看代表成果和项目如何支撑研究方向
  → 展开合作网络发现跨院系连接
  → 点击一条关系，回到证据和来源
```

这条叙事同时表达人才发现、知识组织、关系洞察和可信追溯四种价值，但底层仍是最终平台的公共数据与能力契约。

## 5. 首期数据切片

建议建立 `scholargraph-demo-v1` 版本化 synthetic 数据集，使用固定 UUID 和明确说明：

- 6 位 synthetic 学者，覆盖 4 个院系；
- 4 个院系、3 个学科、6 个研究主题；
- 12 项代表成果、6 个科研项目；
- 至少 45 条事实或分析关系；
- 至少 30 条对象/关系证据；
- 至少一条跨院系合作路径和一条研究主题—项目—成果证据链；
- 一个待确认方向或低置信度关系，用于展示事实与推断分层；
- 所有对象、来源、证据和关系均标记 `synthetic=true`、`dataset_version=scholargraph-demo-v1`。

页面计数必须从当前可见对象/关系计算，不能沿用 fixture 中 86、113 等未落库的大数。

## 6. 产品级公共能力

建议在通用知识/图能力之上增加薄的 `scholars` 场景模块，不建立独立数据库：

| 能力 | REST 首期映射 | 未来入口 |
|---|---|---|
| `search_scholars` | `GET /api/v1/scholars` | Web、SDK、MCP、Skill、小程序、客户端 |
| `get_scholar_profile` | `GET /api/v1/scholars/{scholar_id}` | Web、SDK、MCP Resource、Agent Tool |
| `get_scholar_network` | `GET /api/v1/scholars/{scholar_id}/network` | Web、SDK、MCP Tool、Skill |
| `get_scholar_evidence` | `GET /api/v1/scholars/{scholar_id}/evidence` | Web、SDK、MCP Resource、Skill |

这些能力组合 PostgreSQL 规范对象、关系、证据和通用 GraphPort；不得复制一套学者事实表，也不得把 HugeGraph REST/Cypher 暴露到公共接口。

## 8. 明确不进入首次 Demo

- 真实学校人事、科研、论文或评价数据接入；
- 学者身份归并和成果认领的真实业务流程；
- 人才引进适配度、人才价值、发展潜力或推荐等级；
- 排名、绩效评价、资源配置建议和自动管理结论；
- 学者比较任务、纠错审批、报告生成和导出；
- LLM 生成画像、合作推荐或智能问答；
- 真实认证、统一策略层、通用任务平台；
- 七类应用和五类角色入口的完整实现。
