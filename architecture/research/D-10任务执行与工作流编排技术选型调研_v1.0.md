# D-10 任务执行与工作流编排技术选型调研 v1.0

- 状态：调研完成；路线确认与开发延后至首次 Demo 之后
- 日期：2026-08-26
- 范围：后台任务、数据加工、人工确认和长流程；不替代 D-06 数据连接器或未来 Agent Runtime

## 1. 结论先行

项目负责人已决定：**本次 Demo 重点演示“学者星图”，D-10 的路线确认和开发均延后。** 首次 Demo 保留现有 `async_job`、Outbox、专用投影 worker 和明确标注的前端模拟任务，不补建通用任务状态机、SSE 或外部工作流引擎。

恢复 D-10 时，建议重新确认 **SmartLib PostgreSQL 持久任务状态机 + 幂等 Python worker** 首选提案；Temporal、Camunda、Airflow/Dagster 仍按流程类型触发 POC。本调研作为恢复决策的输入，不构成当前实施授权。

恢复后的首期候选不是再写一个“大型自研工作流引擎”，而是把已经存在的 `async_job`、Outbox 和 worker 骨架补成一个边界明确、可退出的真实任务闭环：

1. PostgreSQL 保存 SmartLib 任务的权威状态、步骤、尝试、租约、取消和事件；
2. Python worker 使用并发安全领取、有限租约、心跳、重试退避和幂等键执行；
3. API/SSE 提供创建、查询、取消和进度；Web 用真实任务替换“定时切换 loading/result”的页面模拟；
4. 任务 handler 与调度器分离，未来 Temporal/Camunda/Airflow adapter 复用同一任务类型和业务命令；
5. 大文件/大结果不进入任务表，进入对象存储，表中只保存受控引用和校验信息；
6. 当前搜索/图投影 worker 可暂时独立，后续以同一租约/尝试语义收敛，不把外部引擎作为投影正确性的前提。

## 2. 当前基线与缺口

### 已有基础

- `smartlib.async_job`：job type、state、progress、attempt/max attempts、input/output、failure、requested_by、trace、available/start/finish time；
- `smartlib.outbox_event`：领域写入与事件同事务，投影可重放；
- `/api/v1/jobs/{job_id}`：按 RLS 查询任务状态；
- 搜索和 HugeGraph 投影 worker：轮询 Outbox、交付、确认；
- Web “知源智研”已有任务入口、loading steps 和结果展示，但当前完全是组件内模拟。

### 当前缺口

- 没有创建任务的通用 application service、handler registry 或 worker；
- 没有 `FOR UPDATE SKIP LOCKED`/等价领取、lease owner、lease expiry、heartbeat；
- 没有 attempt/step/event 历史，当前行只保留最终错误；
- 没有幂等键、去重范围、超时、取消请求/确认和补偿语义；
- progress 类型数据库为 0–1 numeric、API 模型为 int，契约存在不一致风险；
- 没有任务输入/输出 schema version、handler version、data/policy/model version；
- 没有 SSE 进度或 Web 真实任务链路；
- projection worker 的异常处理会退出进程，没有统一 retry/dead-letter/operator action；
- 没有备份恢复后继续执行、worker 崩溃接管或双 worker 竞争测试。

因此现有表证明了方向，但不证明任务平台已经实现。

## 3. 三类工作负载不能混为一类

| 类型 | SmartLib 示例 | 核心语义 | 首期/未来 |
|---|---|---|---|
| 短后台任务 | 导出、报告生成、局部重建 | 秒到分钟、有限重试、状态/进度 | SmartLib task worker |
| 数据/投影任务 | 质量运行、批量规范化、搜索/图重建 | 批次、检查点、幂等、可重建 | 当前 worker；复杂 DAG 后评估 Airflow/Dagster |
| 业务/AI 长流程 | 文献资料包、画像审核、成果匹配、人工批准、Agent 任务 | 小时到天、等待外部事件/人工、取消、恢复 | 简单状态机；复杂后评估 Temporal/Camunda |

数据连接器的源端检查点仍属 D-06；Agent 的工具选择、预算和逐次批准仍属 D-14。D-10 只提供可靠运行和可观察状态，不吞并领域决策。

## 4. 候选路线比较

| 路线 | 最适合 | 优势 | 当前代价/边界 | 建议 |
|---|---|---|---|---|
| A. PostgreSQL task state machine + Python worker | 当前模块化单体、有限任务类型 | 复用 PG18、RLS、审计、备份；与业务事务/Outbox一致；组件少 | 必须自行严谨实现 lease、retry、cancel、history、idempotency；不适合无限扩展成 BPMN/DAG 平台 | **当前首期主路线** |
| B. Temporal | 代码化、长时间、故障恢复、外部事件、复杂补偿/Agent 流程 | Durable execution、事件历史、timer/signal、worker 可恢复 | 新服务/持久存储/可观测/升级；workflow determinism 和版本治理有学习成本 | 技术长流程触发后 POC |
| C. Camunda 8 | BPMN、业务人员协作、用户任务、表单、审批 | 可视流程、用户任务/指派/期限、服务任务 | 自托管组件和运维面大；BPMN/FEEL/worker 体系；版本/许可和身份集成需核验 | BPMN/人工流成为产品核心后 POC |
| D. Airflow 3 | 定时批处理 DAG、数据平台已有运维 | 调度、依赖、重跑、回填、UI、生态 | 最小部署已有 scheduler、DAG processor、API server、metadata DB；不适合作为产品交互任务总线 | 学校已有或数据 DAG 规模触发 |
| E. Celery/RQ/Dramatiq 类队列 | Python 异步投递 | 成熟队列消费、重试、并发 | 仍需 broker/result backend 和业务状态机；不能自动解决人工等待、版本、审计 | 当前不单独引入 |

Temporal 官方将其定位为 durable execution：故障后从事件历史恢复长期运行应用，并支持自托管或云服务（[Temporal Documentation](https://docs.temporal.io/)）。这类能力对复杂 Agent/长流程有价值，但当前没有足够流程复杂度证明新增集群合理。

Camunda 8 的用户任务会让流程实例等待人工完成，支持指派、候选组、期限、优先级和表单；服务任务通过 job worker 执行，而 job 可能至少一次投递，handler 必须幂等（[Camunda User Tasks](https://docs.camunda.io/docs/components/modeler/bpmn/user-tasks/)、[Camunda Job Workers](https://docs.camunda.io/docs/components/concepts/job-workers/)）。这适合业务可视 BPMN，而不是仅为一个 Demo loading 动画部署。

Airflow 以 DAG、task、scheduler、DAG processor、API server 和 metadata database 组织批处理工作流，适合调度/回填/数据任务；其最小架构本身已有多个组件（[Airflow Architecture](https://airflow.apache.org/docs/apache-airflow/stable/core-concepts/overview.html)）。如果学校已有 Airflow，可作为未来数据 DAG adapter；SmartLib 产品任务仍需自己的稳定状态 API。

## 5. 产品中立任务合同

### 5.1 创建命令

```text
job_type
input + input_schema_version
requested_by + channel + purpose
idempotency_key + idempotency_scope
trace_id
priority
not_before / deadline / timeout
handler_version
data/policy/model versions（按任务适用）
```

客户端不能自行指定 handler、最大重试、执行账号或任意命令。`job_type` 必须来自服务端 registry，并绑定输入 schema、许可、超时、重试、取消和输出策略。

### 5.2 状态机

```text
queued -> running -> succeeded
  |          |  \-> retry_wait -> queued
  |          |  \-> failed
  |          |  \-> cancel_requested -> cancelled
  |          \----> waiting_external / waiting_approval（触发复杂度后启用）
  \---------------> cancelled
```

状态迁移只能通过带前置状态和版本的事务命令发生。终态不可倒退；重新执行创建新 attempt 或新 job，不静默改写历史。

### 5.3 运行数据

- `job`：业务任务聚合与当前状态；
- `job_attempt`：每次领取、worker、开始/结束、错误分类；
- `job_step`：可展示步骤和进度，不保存敏感原文；
- `job_event`：append-only 状态事件；
- `job_artifact`：对象存储引用、media type、checksum、许可/可见性；
- lease：owner、token、expires_at、heartbeat_at；
- idempotency：scope + key 唯一，返回同一业务结果而非重复副作用。

## 6. 延后前曾提出的展示闭环（当前不实施）

以下方案保留为后续参考，不属于本次学者星图 Demo：

1. 用户提交 synthetic 研究问题；
2. API 创建 `research_brief_demo` 任务并立即返回 `202 + job_id`；
3. worker 依次记录“解析范围—核验许可—检索材料—组织证据”；
4. Web 使用 SSE/轮询展示真实数据库进度；
5. 结果来自当前 synthetic 资源与真实治理 API，明确标记未调用真实模型；
6. 取消、失败、重试和过期至少各有一个演示/测试哨兵；
7. 每个任务可追溯 requested_by、trace、数据版本、许可状态和产物。

这条链路能展示平台任务价值，但不得把固定预制结果表述为 AI 实时研究结论。

## 7. 外部引擎触发条件

### Temporal

- 多个流程持续小时/天并等待 timer、signal、外部回调；
- 补偿、子流程、并行/竞速和跨服务恢复显著复杂；
- Agent 任务需要持久暂停/恢复和代码工作流版本治理；
- 已有可承担 Temporal 服务、存储、升级、备份和可观测性的团队。

### Camunda

- BPMN 是业务/馆员共同设计和审核的正式语言；
- 大量用户任务需要候选组、认领、转派、期限、表单和运营报表；
- 学校确认 Camunda 版本、许可、身份、搜索/数据库和自托管运维边界。

### Airflow/Dagster

- 出现多条定时数据 DAG、回填、分区、依赖、SLA 和数据平台运维需求；
- 学校已有平台可复用，或规模证明独立部署收益高于 SmartLib worker；
- 数据 DAG 不承担面向用户的交互任务状态权威。

## 8. 当前延后边界与恢复条件

本次 Demo 不实施 durable job contract、通用 worker、API/SSE 或 Web 真实任务切片，也不引入任意 DAG 编辑器、BPMN、分布式事务、通用脚本执行、动态插件市场或无限嵌套流程。现有专用图投影 worker 继续服务学者星图，但不得据此宣称通用任务平台已经完成。

D-10 在出现真实后台任务、多入口统一任务状态、批量画像/图投影超出现有 worker 能力、真实数据加工与回填、人工确认/长流程，或正式的幂等与故障恢复验收要求时恢复。
