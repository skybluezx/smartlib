# D-03 主数据库技术选型调研 v1.0

- 状态：已完成，决策见 ADR-0002
- 日期：2026-08-25
- 关联决策：D-03
- 决策结论：PostgreSQL 18

## 1. 这项决策解决什么

SmartLib 主数据库不是搜索索引、图数据库、向量库或原始文件仓库。它保存平台自身的权威状态，并允许其他派生系统从中重建：

- 数据源登记、统一对象和来源映射；
- 事实、分析、推断与人工确认的分层记录；
- 关系事实、候选关系与证据引用；
- 画像快照、规则版本、有效时间和系统时间；
- 许可、可见性、审核状态和策略版本；
- 异步任务、Outbox 事件、导出与审计索引。

首版需要真实持久化、迁移、权限纵深、备份恢复和后续 CDC 能力。数据量尚不足以证明需要分布式数据库，搜索、图和向量仍是可重建投影。

## 2. 决策前提

### 已确认的架构要求

1. 关系模型是规范主干，可演进来源字段使用 JSON，而不是把所有数据做成无模式文档。
2. 许可和可见性需要应用授权之外的数据库纵深防护。
3. 所有结构变更通过版本化 migration 管理。
4. 数据库必须支持全量备份、日志归档和时间点恢复路径。
5. 后续搜索、图谱、数据仓库和事件系统应能读取增量变化。
6. 首版使用单实例不等于放弃未来主备、高可用和 Kubernetes 演进。

### 仍需学校确认

- 数据库白名单、信创或国产化是否为首版硬约束；
- 学校是否已有统一 PostgreSQL、openGauss/GaussDB、达梦、人大金仓或 OceanBase 服务；
- 是否要求购买商业支持；
- 试点环境 RPO、RTO、数据规模和日增量。

## 3. 候选方案

### A. PostgreSQL 18（推荐）

适配点：

- `jsonb` 使用二进制分解格式，支持 GIN 索引和 `jsonpath`，适合保存来源扩展字段，但核心对象仍可保持规范关系模型；
- 原生 Row-Level Security 可覆盖 `SELECT`、`INSERT`、`UPDATE`、`DELETE`，启用后无匹配策略时默认拒绝；
- 内置物理与逻辑复制，逻辑复制可按表发布并保持单订阅内事务顺序；
- 官方备份体系覆盖 SQL dump、文件系统备份、连续 WAL 归档和 PITR；
- Java、Python、迁移工具、CDC、监控、连接池和容器生态成熟；
- 与后续 pgvector、Apache AGE 等候选有自然 POC 路径，但主库决策不等于提前确认这些扩展。

风险：

- 若学校有强制国产数据库目录，正式部署可能不被接受；
- RLS 策略存在表所有者/超级用户绕过、复杂策略并发和隐蔽通道风险，必须配合专用应用账号、策略服务和测试；
- 逻辑复制不自动复制 DDL 和 sequence，migration 与复制运维需单独设计。

### B. openGauss（国产化明确要求下的首要 POC 候选）

适配点：

- 官方文档提供 PostgreSQL 客户端/API 兼容、行级访问控制、逻辑复制、物理备份和 PITR；
- 具备主备、安全审计、动态脱敏与国产生态路线；
- SQL 和 JDBC 层与 PostgreSQL 有一定迁移基础。

必须验证的差异：

- 官方 RLS 文档明确其策略不作用于 `INSERT` 和 `MERGE`，且每表最多 100 条策略；这与 PostgreSQL 的完整写入检查语义不同；
- “兼容 PostgreSQL API”不等于 SQL、扩展和运维完全兼容；例如官方 `postgres_fdw` 说明目前只支持 openGauss 之间连接，不支持 openGauss 与 PostgreSQL 直连；
- JSONB 操作符、索引、Flyway、Hibernate、连接池、CDC、监控、ARM64/容器镜像和备份工具必须以项目实际版本 POC；
- 不应同时维护 PostgreSQL/openGauss 两套生产方言，除非学校确有双环境交付要求和对应测试预算。

### C. MySQL 8.4 LTS / MariaDB

适配点：

- 事务、JSON、复制、备份与 PITR 成熟，学校运维团队通常容易获得经验；
- 如果学校只有受管 MySQL 服务，可降低基础运维门槛。

不推荐作为默认主库的原因：

- MySQL 官方权限粒度为全局、数据库、表、列和存储程序，不提供 PostgreSQL 同类的通用原生 RLS；SmartLib 的记录级许可纵深需要更多视图、存储程序或应用逻辑；
- JSON 查询、索引、迁移脚本、Outbox/CDC 和后续扩展路线均需从 PostgreSQL 方案重写或重新验证；
- 对本项目没有已被数据规模证明的独特收益。

### D. OceanBase 或其他分布式数据库

适用条件：学校已有受管平台、明确要求分布式容灾，或真实压测证明单机/主备关系库不足。

当前不作为首版默认方案：SmartLib 尚无吞吐、容量或跨地域写入证据证明需要分布式复杂度；OceanBase 的 MySQL/Oracle 兼容模式也不是 PostgreSQL 方言，迁移和权限模型需重新验证。

### E. 达梦、人大金仓、GaussDB 等学校指定商业数据库

这些不是一个可合并评价的技术选项。若进入学校白名单，应先取得准确产品、版本、部署形态、驱动、授权和支持合同，再用同一套验收清单 POC。不能仅凭“兼容 PostgreSQL/Oracle”承诺可替换。

## 4. 面向 SmartLib 的比较

下表分值是基于当前 SmartLib 需求的架构判断，不是通用数据库排名。5 为最匹配。

| 维度 | PostgreSQL 18 | openGauss | MySQL 8.4 | OceanBase/其他分布式 |
|---|---:|---:|---:|---:|
| 规范关系 + 可索引 JSON | 5 | 4，需版本 POC | 4 | 4 |
| 记录级许可纵深 | 5 | 3，写入语义需补齐 | 2 | 3，依模式而定 |
| 双时间/证据/审核模型 | 5 | 4 | 4 | 4 |
| migration 与开发生态 | 5 | 3 | 5 | 3 |
| CDC/投影重建路径 | 5 | 4 | 5 | 4 |
| 首版部署运维成本 | 5 | 3 | 5 | 2 |
| 国产化适配 | 2，取决于校规 | 5 | 2，取决于产品 | 5，取决于产品 |
| 当前总体匹配度 | **推荐** | **条件候选** | 备选 | 暂不引入 |

## 5. 建议决策

建议确认：

> SmartLib 首版主数据库采用 PostgreSQL 18。PostgreSQL 保存平台权威状态；对象存储保存原始文件和大对象；搜索、图和向量系统只保存可重建投影。若学校存在强制国产化/白名单要求，则在进入试点生产前，以同一领域模型、migration、权限和恢复验收清单对学校指定数据库进行 POC，再通过新 ADR 决定迁移，而不是声称数据库可无损替换。

选择 PostgreSQL 后仍保留以下退出边界：

- 领域服务不向上层入口暴露数据库表或数据库方言；
- Web、Public API、MCP、Skill、Agent、小程序和客户端统一经过平台能力层；
- 使用 Flyway 版本化 migration，禁止应用启动时隐式修改生产 schema；
- 核心数据使用标准关系类型，`jsonb` 仅承载来源扩展字段；
- PostgreSQL 特有能力集中登记，并为国产数据库 POC 建立兼容清单；
- 数据导出使用开放格式和稳定标识，派生投影始终可重建。

不建议采用“开发 PostgreSQL、生产未知数据库但先假定兼容”的双数据库路线。它会让 RLS、JSON、索引、DDL、锁、CDC 和恢复差异延迟到上线阶段暴露。

## 6. 实施结果

D-03 于 2026-08-25 确认并完成首个数据库底座任务：

1. Compose 已加入 PostgreSQL 18.6、命名卷、健康检查和内部网络，未映射主机 5432；
2. `database/migrations` 已由 Flyway 13 管理，空库迁移和独立 validate 均通过；
3. 已建立 `source_system`、`knowledge_object`、`source_reference`、`evidence_record`、`relation_assertion`、`relation_evidence`、`policy_tag`、`object_policy_tag`、`async_job`、`outbox_event` 和 `audit_event`；
4. 有效时间、系统时间、事实类别、审核状态、版本、JSON 类型和关系目标均有数据库约束；
5. 已建立 owner、应用读写、只读和审计读取的无登录权限角色；
6. 已建立并验证 14 条 RLS 策略，RLS 仍仅作为许可策略服务之外的纵深防护；
7. 已验证只读拒写、审计不可变、Outbox 原子回滚、容器重建持久化和隔离恢复；
8. Web 仍不直接访问数据库，后续由 D-01 平台核心 API 接入。
