# ADR-0002：PostgreSQL 18 作为平台主数据库

- 状态：已接受
- 日期：2026-08-25
- 决策人：项目负责人
- 关联编号：D-03

## 背景

SmartLib 需要保存数据源登记、统一对象、来源映射、事实与推断、证据、画像版本、许可、审核、任务、Outbox 和审计索引。这些数据是平台自身的权威状态；搜索、图和向量系统是可以重建的服务投影，原始文件和大对象进入 S3 兼容对象存储。

首版数据量尚不足以证明需要分布式数据库，但从第一版开始必须具备真实持久化、版本化迁移、记录级权限纵深、备份恢复和增量输出路径。

## 候选方案

1. PostgreSQL 18；
2. openGauss 或学校指定国产数据库；
3. MySQL 8.4/MariaDB；
4. OceanBase 等分布式数据库。

详细比较见《D-03 主数据库技术选型调研 v1.0》。

## 决策

SmartLib 首版采用 PostgreSQL 18 作为平台主数据库：

- PostgreSQL 保存 SmartLib 平台权威状态；
- 原始文件和大对象不进入主库，进入 S3 兼容对象存储；
- 搜索、图、向量和聚合视图只保存可重建投影；
- 使用 Flyway 管理所有 schema migration，禁止应用启动时隐式修改生产 schema；
- 核心模型使用规范关系结构，`jsonb` 仅保存来源扩展、证据扩展和任务参数；
- 采用无登录权限角色区分 owner、应用读写、只读和审计读取；
- RLS 是应用授权之外的纵深防护，不代替许可策略服务；
- 首版单实例运行不代表最终高可用结论，后续按 RPO/RTO 建设主备、WAL 归档和 PITR；
- 当前容器镜像固定 PostgreSQL 18 的具体补丁版本，补丁升级必须经过 migration、备份和恢复测试。

## 国产化边界

如果学校正式部署存在强制数据库白名单，不假设其他数据库可通过更换连接串无损替代 PostgreSQL。应取得准确产品、版本、部署形态和驱动，以同一领域模型、migration、RLS/许可、CDC、备份恢复和性能用例完成 POC，再通过新 ADR 决定迁移。

数据库特有能力应集中登记；领域能力不得向 Web、Public API、MCP、Skill、Agent、小程序或客户端暴露表结构和数据库方言。

## 初版运行约束

- PostgreSQL 仅加入 Compose 内部网络，默认不向主机或公网暴露 5432；
- PostgreSQL 18 数据卷挂载到 `/var/lib/postgresql`，匹配官方镜像 18+ 的版本化 `PGDATA` 结构；
- bootstrap 账号只用于本地初始化和 migration，不作为应用账号；
- 开发示例密码不得用于共享、演示生产或正式环境；
- 任何表都不默认向 `PUBLIC` 授权；
- 权威历史表不向应用角色授予物理删除权限；
- 审计事件只追加，应用角色不能更新或删除。

## 后果

### 正面

- 首版即可使用关系约束、JSONB、RLS、事务、Outbox、逻辑复制和 PITR 路径；
- Java、Python、CDC、迁移、监控和容器生态成熟；
- 领域状态与派生索引之间的权威边界清晰。

### 代价与风险

- PostgreSQL 特有 SQL 会增加国产数据库迁移成本；
- RLS 策略需要与应用连接池、事务级身份上下文共同测试；
- 单实例 Compose 不提供生产高可用；
- Flyway、数据库镜像和备份工具都需要纳入供应链与版本升级管理。

## 验证要求

1. Flyway 能从空库完成全部 migration，并通过 validate；
2. PostgreSQL、migration 和 Web 的 Compose 依赖关系正确；
3. 数据库容器重建后命名卷数据仍存在；
4. 约束拒绝无效事实类别、时间范围和关系目标；
5. RLS 能按事务级 actor 隔离私有记录；
6. 只读角色无法写入，应用角色无法更新或删除审计事件；
7. 领域写入与 Outbox 事件可以在同一事务提交或回滚；
8. `pg_dump` 备份能恢复到隔离数据库并通过结构与数据检查。
