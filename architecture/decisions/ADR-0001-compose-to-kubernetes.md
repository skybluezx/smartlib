# ADR-0001：Docker Compose 起步、Kubernetes 演进

- 状态：已接受
- 日期：2026-08-25
- 决策人：项目负责人
- 关联编号：D-11

## 背景

SmartLib 当前需要把可展示 Web 纳入最终系统的真实工程结构，并逐步建设数据、知识、检索、AI 与多入口能力。首版需要在开发机、集成环境和少量服务器上快速、可重复运行，但目前尚未确认学校 Kubernetes、存储、网络、监控和运维团队的成熟度。

如果首版直接以完整 Kubernetes 集群为运行前提，将提前引入集群、入口、证书、持久卷、密钥、监控和发布运维成本；如果继续只用开发服务器临时运行，又无法形成向最终生产环境迁移的标准部署单元。

## 候选方案

### 方案 A：Docker Compose 起步，Kubernetes 演进

所有应用从第一天开始生成标准容器镜像。开发、集成和首版展示使用 Compose；学校级运行条件成熟后，复用相同镜像、配置键、健康检查和可观测性约定迁移到 Kubernetes。

### 方案 B：首版直接使用 Kubernetes

立即建设完整 Kubernetes 清单和集群运行链路。长期形态更早可见，但在基础设施和运维责任尚未确认时，首版成本和阻塞风险更高。

### 方案 C：继续使用本地进程和临时服务器

开发速度短期最快，但环境不可重复，依赖和配置容易漂移，后续容器化需要返工。

## 决策

采用方案 A：

- 开发、集成和首版展示以 Docker Compose 为基线；
- 应用均构建为标准、非特权容器镜像；
- 配置通过环境变量或挂载配置注入，不写入镜像；
- 每个长期运行服务必须提供健康检查；
- 数据持久化、备份、密钥和可观测性在相关技术决策后加入；
- Kubernetes 清单在学校级运行阶段建设，但必须复用同一镜像和配置契约；
- Compose 不被视为最终高可用方案。

## 后果

### 正面

- 首版可在较低运维成本下形成可重复运行环境；
- 镜像成为开发、测试和后续生产的共同交付单元；
- 不在数据库、搜索、图谱和后端语言决策前提前锁定产品；
- 后续 Kubernetes 迁移有明确兼容边界。

### 负面与债务

- Compose 本身不提供跨节点调度、自动伸缩和学校级高可用；
- Kubernetes 网络、存储、入口和发布策略仍需后续设计；
- 本地 Docker 服务是首版容器验证的运行依赖。

### 退出/替换方案

当学校 Kubernetes 或其他容器平台具备明确运维责任、存储类别、入口、证书、监控和灾备能力后，为同一镜像增加 Helm/Kustomize 清单。Compose 保留为本地开发与集成测试工具。

## 验证方法

- Compose 配置能够完成结构解析；
- Web 镜像能够从干净构建阶段生成；
- 容器启动后健康检查返回成功；
- SPA 路由回退到 `index.html`；
- 容器停止和重新启动后行为一致；
- 后续每加入一个基础服务，都必须补充健康检查、持久化和恢复验证。
