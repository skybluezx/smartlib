# ADR-0007：数据接入与连接器框架路线

- 状态：局部重新打开（受控文件案例CF-01；通用连接器与SeaTunnel POC仍延后）
- 日期：2026-08-26
- 决策人：项目负责人
- 关联编号：D-06

## 背景

SmartLib 需要接入学校业务系统、图书馆电子资源、机构知识库、正式 API 和受控文件。现有系统只有数据源登记和通用任务表，尚无连接器能力声明、运行批次、检查点、清单、模式漂移和接入发布门。第三方数据移动工具不能表达 SmartLib 的许可、证据、责任和知识对象语义。

## 原提议路线

采用 SmartLib 自有连接器契约与 Python SDK 作为长期稳定边界，首批正式 API/受控文件连接器由平台原生 worker 实现；固定 Apache SeaTunnel 2.3.13 + Zeta 作为 JDBC、文件、批量与 CDC 的 POC 数据移动执行器。

Airbyte 与 NiFi 暂不进入首轮：Airbyte 由多个真实 SaaS/API 源及其官方稳定连接器覆盖触发；NiFi 由既有校级平台或边缘路由、持久缓冲、背压和 provenance UI 的真实需求触发。

本决策只确认 POC 路线，不表示 SeaTunnel 已成为生产接入平台。

## 当前决定（2026-08-26）

项目负责人决定：为了优先形成可展示的最终平台初版，Demo 阶段暂时跳过 D-06 外部数据接入产品与 SeaTunnel POC，不在当前迭代部署 SeaTunnel，也不实现真实源连接器。

这是实施顺序延后，不是否决本 ADR 的稳定连接器契约、控制面和安全边界。进入首批真实数据接入前，必须重新打开 D-06，确认当时的 SeaTunnel 版本、真实源条件、学校基础设施和许可要求。

## CF-01局部重新打开记录（2026-09-01）

项目负责人指定《2026国自然代表性论著全部信息_283篇.xlsx》作为学者星图首个真实受控文件案例。本阶段只从工作表“全部论著（283篇）”B列“获批人”提取姓名，登记真实但受限、待身份核验的学者对象；不扩展到论文、作者、院系、职称、项目或推断关系。

本次局部重新打开不启动SeaTunnel，也不代表通用连接器控制面已经完成。导入采用版本化清单、源文件SHA-256、稳定UUID、来源引用、逐对象证据、Outbox和审计记录；同名只做精确检测，不自动合并。来源责任部门、正式展示许可和统一人员标识未提供，因此数据源授权状态保持`pending`，对象保持`restricted`、`unverified`和`pending`。后续扩大真实数据范围前仍需完成通用接入运行、清单、错误、检查点和发布门设计。

Demo 模拟数据必须遵守以下临时边界：

- 使用版本化、可重复执行的种子数据集，明确标记 `synthetic`；
- 通过平台应用服务或正式导入边界写入 PostgreSQL，不把业务数据新增为前端硬编码数组；
- 使用真实稳定 ID、来源、证据、关系、可见性、许可标签、版本和审计字段；
- 继续触发真实 Outbox、OpenSearch/图投影、权限过滤和公共 API；
- Web、API、未来 MCP/Skill/Agent 消费同一能力，不增加 Demo 专属业务接口；
- 模拟数据能够整体清理或替换，不能与未来真实数据共用未区分的来源身份；
- 页面和对外展示必须明确说明哪些数据是模拟数据，不能让领导或用户误认为已接入真实学校系统。

## 必须保持的边界

- FastAPI/PostgreSQL 掌握数据源、连接器、运行、许可、清单、检查点、错误和发布状态；
- 凭据只保存密钥引用，连接器配置、日志、清单和审计不得出现明文密钥；
- 执行器只输出版本化接入信封或写受控落地区，不直接写 SmartLib 权威对象表；
- 外部交付采用至少一次语义，规范提交按稳定幂等键去重；
- 检查点在接入数据和清单持久化后推进，不能因进程内读取成功提前确认；
- 删除/撤回使用显式 tombstone；模式漂移默认隔离；
- 数据范围、字段、许可用途、保存期限和展示边界随每个运行留存；
- 首选正式 API、学校数据交换体系和受控文件，默认不直接读取业务系统生产数据库；
- SeaTunnel、Airbyte、NiFi 或未来执行器都通过 `ConnectorExecutorPort` 适配，不能泄漏产品作业模型到公共 API。

## 重新打开 D-06 后的首期实现范围

1. 定义连接器协议、能力描述、接入信封、清单和契约测试套件；
2. 在 PostgreSQL 增加连接器定义/实例、运行、检查点、记录清单和错误表；
3. 发布数据源发现、连接测试、启动接入和运行状态能力；
4. 建立原生 Python worker 与一个受控文件样例连接器；
5. 用相同信封契约接入 SeaTunnel 2.3.13/Zeta POC；
6. 获得首批正式数据源后运行全量、增量、失败恢复、漂移、删除和许可测试；
7. POC 后再决定 SeaTunnel 的生产角色和是否加入 Airbyte/NiFi。

## 接受门槛

以《D-06 数据接入与连接器 POC 验收方案 v1.0》为准。任何未授权数据接入、明文凭据泄漏、记录静默丢失、重复规范对象、错误检查点推进、删除遗漏、模式漂移静默吞没或无法追溯到源批次，均否决该执行路线。

## 退出方案

- SeaTunnel 收益不足：首版保留 Python SDK + 原生 worker，只接少量正式源；
- 标准连接器数量快速增长：重新评估 SeaTunnel 生产化或 Airbyte；
- 学校已有合规 NiFi/数据交换平台：通过 `ConnectorExecutorPort` 接入，不重做 SmartLib 控制面；
- 所有情况下，接入清单、检查点、许可和规范对象责任仍留在 SmartLib。
