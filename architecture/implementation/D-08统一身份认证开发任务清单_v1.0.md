- 日期：2026-08-26
- 目标：恢复 D-08 后，把现有 synthetic Demo 身份 seam 演进为可替换学校 IdP 的真实认证骨架，不等待或伪造学校生产协议；当前不启动以下代码批次

## 1. 当前代码落点

| 层 | 当前状态 | D-08 改造落点 |

| 审计 | `actor_id` 可记录，但无主体类型/委托结构 | 保持 append-only；新增 client、principal type、delegation 和 auth context 安全摘要 |
| OpenAPI | 每个受保护操作暴露 actor header | 改为统一 OAuth2/OIDC bearer security scheme；登录/会话端点单独描述 |
| Web | 顶部角色下拉是展示视角；客户端直接请求 API | 增加 `/auth/session` 驱动的真实用户状态；BFF 同源会话；角色下拉明确降级为 Demo 视角 |

## 2. 实施批次与提交边界

### 批次 A：认证领域与数据库身份主键

1. 新建 `smartlib_platform/identity` 模块：models、ports、service、errors；
2. 定义 `PrincipalContext` 和 `IdentityProviderPort`，领域模块不得导入 Authlib/Keycloak 类型；
3. 创建 V10 migration：
   - `smartlib.principal`；
   - `smartlib.external_identity`，唯一键为 `(issuer, subject)`；
   - `smartlib.affiliation_snapshot`；
   - `smartlib.service_principal`；
   - 受控身份绑定审计/状态；
4. 为现有 Demo UUID 建立显式 development principal seed，保持已有 synthetic 对象和 RLS 可读；
5. 数据库连接事务只接受已构造的内部 `principal_id`；
6. 增加冲突、停用、未知主体、不同 issuer 相同 sub 的数据库测试。

**退出条件：** 现有 UUID 不丢失、不重写业务对象；身份映射可重复执行；没有 email/姓名唯一约束；RLS 回归全通过。

### 批次 B：资源服务器令牌验证

1. 新建受信 issuer 配置和启动时配置校验；
2. 实现 discovery/JWKS 获取、缓存、允许算法白名单和轮换；
3. 验证 signature、issuer、audience、exp/nbf/iat、token type、client 和 scope；
4. 从 claims 归一 human/service/agent/delegated 主体；
5. 认证失败统一返回无敏感细节的 401/403，并记录安全审计；
6. OpenAPI 增加 bearer security scheme，移除生产 actor header；
7. development authenticator 独立实现，只有 `auth_mode=development` 可注册。

**退出条件：** POC 验收方案列出的全部错误令牌 100% 拒绝；合法 token 进入现有数据库事务并维持 RLS；令牌原文零日志。

### 批次 C：Web BFF 会话

1. 实现 `/auth/login`、`/auth/callback`、`/auth/session`、`/auth/logout`；
2. Authorization Code + PKCE S256、state、nonce、精确 redirect URI；
3. 服务端 session store；浏览器 Cookie 设置 Secure、HttpOnly、SameSite 和固定 path/domain；
4. access/refresh token 加密或保存在服务端受控会话存储，不进入浏览器；
5. CSRF、会话固定、并发刷新、绝对/空闲超时、登出和失败恢复；
6. 若 BFF 代理 API，使用固定路由映射和目标白名单，不接受任意 URL；
7. Web 增加登录、加载、过期、拒绝和登出状态；可访问性与移动端回归。

**退出条件：** 浏览器 storage/源码/网络 URL 无 token；会话 Cookie 安全属性和 CSRF 负向测试通过；Demo 视角选择器不再声称改变真实身份。

### 批次 D：多接口认证适配

1. Public API/SDK：标准 bearer token 和服务主体；
2. MCP/Skill：宿主委托或独立服务主体，不把 token 写入包和提示词；
3. Agent：用户 + Agent 双主体和 delegation chain；
4. 小程序：只定义绑定/交换端口与专用 audience，未决定产品入口前不写平台专用实现；
5. 原生客户端：外部浏览器 + PKCE 契约和 redirect 注册规范；
6. capability catalog 增加 authentication requirements、audience、scopes 和主体类型。

**退出条件：** 各入口共享同一 `principal_id` 与审计语义，适配器不能绕过 authentication service 或直连数据库。

### 批次 E：学校 SSO 或条件代理联调

1. 用信息采集表取得学校权威事实；
2. 学校 direct OIDC 合同时，替换本地 issuer 配置并跑同一契约测试；
3. 只有 ADR 触发条件成立时启动 Keycloak/校级代理 POC；
4. 验证 MFA/acr、停用传播、claims、登出、密钥轮换和故障路径；
5. 完成运维手册、密钥/证书轮换、备份恢复和安全事件责任矩阵。

**退出条件：** 学校联调证据不能被本地测试 issuer 结果替代；Keycloak 未触发时不得成为默认依赖。

## 3. Python 库选择的小型 POC

实现层建议同场验证两个边界，而不是手写 OAuth/OIDC：

| 选项 | 覆盖能力 | 优点 | 局限 | 建议 |
|---|---|---|---|---|
| Authlib | Starlette/FastAPI OAuth/OIDC client、Authorization Code/PKCE、ID Token/JOSE | 一套库覆盖 Web BFF 登录，已有 HTTPX/Starlette 集成 | 能力面较大；版本升级和 Python 3.14 兼容必须实测；仍需自行设计服务端 session | **BFF 主候选** |
| PyJWT | JWT/JWKS 验签与 claims 校验 | 资源服务器边界小、API 清晰、JWKS 缓存/刷新现成 | 不提供完整 Web OIDC client/BFF 流程 | **API 验证基线候选** |
| 全手写协议 | 可完全定制 | 表面依赖少 | state/nonce/PKCE/JWKS/轮换/错误处理极易遗漏，安全维护成本最高 | 排除 |

POC 要求在当前 Python 3.14/FastAPI 版本实际安装、类型检查、负向测试和密钥轮换后再锁版本。Authlib 官方文档提供 Starlette/FastAPI OIDC client、metadata 与 PKCE 支持；PyJWT 官方文档提供 `PyJWKClient`、JWKS 缓存刷新及 issuer/audience 验证。最终可采用 Authlib 同时完成两端，或 Authlib(BFF)+PyJWT(API)，以“更少安全自研、负向测试完整、依赖边界清晰”为准，不按依赖数量拍板。

## 4. 兼容迁移顺序

```text
V10 身份表 + Demo principal
  -> identity port/service（仍由 development authenticator 驱动）
  -> JWT verifier + OpenAPI security scheme
  -> Web BFF/session
  -> 关闭非开发 actor header
  -> 多接口适配
  -> 学校 IdP / 条件代理联调
```

迁移期间 development Demo 保持可运行，但每一步都必须能证明 production 配置不能退回 actor header。不得先删除现有 Demo principal UUID；它们已是业务对象、审计和 RLS 的引用值。

## 5. 回滚与故障边界

- 代码回滚可以切回 development authenticator，但仅限本地环境；不得在生产通过配置开关恢复 actor header；
- 发行者/JWKS 故障时已有、未过期且由受信缓存密钥验证的会话按明确策略处理；未知密钥和新登录失败关闭；
- 身份提供方切换不改变 `principal_id`，通过受控外部身份重新绑定迁移；
- 绑定冲突不自动合并，先冻结并审计；
- Keycloak/代理退出时业务表、RLS 和 Public API 不迁移产品 ID。
